**个人职责：**

## Q1. 为什么用 LangGraph，不用 LangChain？

**项目实际情况：**
- LangGraph 与 LangChain 不是互斥关系：项目实际同时用了两者，`langchain_core.messages` 负责消息抽象与模型调用，LangGraph 负责编排（`durian_langgraph.py`）。
- 选 LangGraph 的真实理由（代码中可验证）：
  1. 显式状态机：`DurianGraphState`（TypedDict + `add_messages` reducer）让会话状态（route_decision、rolling_summary、topic_memories、working_memory 等二十多个字段）全部显式可控，而 LangChain 的 AgentExecutor/ReAct 循环是黑盒。
  2. 检查点持久化：`SqliteSaver` 按 thread_id 落盘（`durian_langgraph_checkpoints.sqlite`），进程重启、页面刷新后可恢复会话，且天然实现多用户会话隔离。
  3. 可插桩可观测：每个节点用 `get_stream_writer()` 往前端推 status 事件（"正在理解问题..." 等），排障时能定位到具体节点。
  4. 需要自定义节点：`trim_memory`（记忆裁剪/摘要）这类节点在 LangChain 链式 API 里没有位置。

**面试回答版本：**
"LangChain 和 LangGraph 我们其实都在用——LangChain 提供消息抽象和模型接入，LangGraph 做编排。不用纯 LangChain 的核心原因是它的 Agent 循环是黑盒：控制流、状态、记忆都在框架内部，我没法做三件事。第一，我们的路由逻辑是'规则优先、模型兜底'的混合策略，需要精确控制每个分支；第二，长会话需要把状态按 thread 持久化，重启后恢复，还要做多用户隔离，LangGraph 的 checkpoint 机制直接给了；第三，我要在生成之后挂一个自己的记忆压缩节点，这在链式 API 里插不进去。所以本质上是要'可控性'：状态显式、流转显式、每一步可观测可测试。"

## Q2. 会话编排怎么做的，为什么不用 ReAct？

**项目实际情况：**
- 图结构（`durian_langgraph.py:545` 附近 `_build_graph`）：`START → route → retrieve → compose → generate → trim_memory → END`，主干为线性流水线，分支逻辑内聚在各节点内部。
- route 节点（`durian_langgraph.py:752`）的决策层次：
  1. 规则优先：闲聊/问候检测（`is_casual_query`）、精确事实检测（`is_exact_query`，命中则切断历史上下文防串扰）、泛化追问检测（`is_generic_followup`，正则匹配"再详细点/为什么/继续"等中英文模式）。
  2. 模型兜底：规则不命中时走 `adapter.route_context`。
  3. 纠错：intent 限定在 `{greeting, casual, new_topic, follow_up}`，`follow_up` 但无上文时强制纠正为 `new_topic`。
- 为什么不用 ReAct：
  1. 任务分布：线上大部分请求是单轮/追问式知识问答，ReAct 每步都让模型决定"想-动-观察"，多出多轮 LLM 调用，延迟和成本不划算。
  2. 确定性与合规：种植园场景有权限边界（工具白名单、敏感操作二次校验），ReAct 的自主决策回路难以保证每次都在白名单内；显式图的每条边都是审计过的。
  3. 可测试：规则路由可以用单测覆盖，ReAct 的 thought 链每次生成都不一样，回归测试困难。
- 折中：单点能力上仍用 function calling 让模型选工具参数，但主控制流不交给模型自由循环。

**面试回答版本：**
"我们的编排是五节点流水线：路由、检索、组装、生成、记忆裁剪。路由节点决定这次是闲聊直答、新话题检索、还是带历史的追问，采用规则优先、模型兜底——比如'再详细点'这种追问用正则就能识别，不用浪费一次模型调用；精确提问会主动切断历史，避免上轮话题污染。不用 ReAct 有三个原因：一是我们八成以上的流量是单轮知识问答，ReAct 的多步思考循环纯粹增加延迟和 token 成本；二是种植园场景有权限合规要求，敏感操作必须走白名单和二次确认，把控制流交给模型自主决策没法保证这一点；三是 ReAct 不可回归测试。我们的折中是：需要动态性的时候用 function calling 选工具和参数，但主流程是确定性状态机，模型只在节点内部干活，不决定'接下来去哪'。"

## Q3. 你的"多轮推理"指什么？

**项目实际情况：**
不是 ReAct 式的多步思考循环，而是跨轮次的上下文推理能力，具体三层：
1. **指代消解与查询重建**：泛化追问（"再详细点"、"为什么"、"然后呢"）本身不含主题，`build_followup_retrieval_query` 会回溯最近一个非泛化的用户轮次，重建出带主题的检索 query；`active_context_card`（活跃上下文卡片）锚定当前话题的锚点词。
2. **历史注入策略按 intent 区分**：`follow_up` 注入历史消息和 topic_memories；`new_topic`/exact 查询反而切断历史，防止上轮的实体串到本轮（比如上轮聊叶腐病、这轮问果期管理，不能把叶腐病带进检索）。
3. **长程状态**：`trim_memory` 节点在每轮后维护 rolling_summary（滚动摘要）、working_memory（工作记忆）、topic_memories（话题记忆），下一轮 route 时重新注入 state，使超出窗口的早期对话仍可被引用。图片诊断场景还有 `use_image_context`，追问可以引用上一轮上传的图片诊断结论。

**面试回答版本：**
"我说的多轮推理不是 ReAct 那种一步一想的循环，而是跨轮次的上下文推理，做了三层。第一层是查询重建：用户说'再详细点'这种没主题的追问，我会回溯到最近一个有内容的轮次，把主题拼回去再检索，而不是拿空查询去搜。第二层是历史注入是有开关的：追问才带历史，识别为新话题时反而主动切断历史，防止上轮的病名、园区名串进这轮检索。第三层是长程记忆：每轮生成后有一个裁剪节点，把超过窗口的旧对话压成滚动摘要和话题卡片，下一轮再注入，这样几十轮之前的结论还能被引用，同时控制了 token 膨胀——这也是我们对话成功率从 60% 提到 97% 的那个机制的一部分。"

## Q4. 用了哪些工具？

**项目实际情况（本仓库可验证的）：**
1. **知识库检索（RAG）**：Milvus + 稠密向量与 BM25 多路召回、RRF 融合，检索作为图上的 retrieve 节点而非模型自由调用。
2. **图像病害诊断**：本地 ResNet50 分类模型（`best_resnet50.pth`）做叶片病害识别，`qwen_vl_max_client.py` 调 qwen-vl-max 做图像理解，诊断结论写入上下文卡片供后续追问引用。
3. **记忆管理工具**：用户长期记忆库（`durian_user_memories.sqlite`，支持"记住/忘掉 XX"的自然语言指令，`extract_explicit_user_memories`、`forget_matching`），含敏感信息标记过滤（密码/token 等不入记忆）。
4. **底层推理设施**：vLLM OpenAI 兼容 server（`start_vllm_openai_server.sh`）承载生成模型；MinerU 做扫描件/文档解析进语料。
5. **评估流水线**：自建 1200+ 条四语种评估集（`qa_dataset_v2.cleaned.jsonl` 等），Hit@1/Hit@3/known-item 多口径回归。

**⚠️ 与简历口径的差异提示：**
简历写了"自然语言下发工单、园区查询、告警查询"。这三类在本仓库代码中没有直接的 tool 实现痕迹（`platforms/` 下是另一套 Dify 相关代码，非本项目运行时）。面试建议口径：这三类是业务侧 API 封装成的工具，工具定义用 JSON Schema 描述、经白名单注册，模型通过 function calling 选择并填参，写操作（下发工单）有二次确认。如果面试官深挖实现细节（如工单系统的表结构、告警数据源），你要能自圆其说或引导到你真正做深的检索/记忆部分。

**面试回答版本：**
"工具分三类。第一类是知识工具：RAG 检索是核心，走 Milvus 稠密加 BM25 多路召回、RRF 融合；另外有图像诊断工具，本地 ResNet50 分类加 qwen-vl-max 视觉理解，结果存成上下文卡片支持追问。第二类是业务工具：任务工单管理、园区查询、告警查询，封装成带 JSON Schema 描述的 function，按角色白名单注册，像下发工单这类写操作有二次确认。第三类是记忆工具：用户可以说'记住我用马来语交流'，系统抽取后写入长期记忆库，密码、token 这类敏感信息有标记过滤。所有工具都挂在 LangGraph 的节点或 adapter 层，模型负责选工具和填参数，但能不能调、调完去哪，由图和权限层决定。"

## Q5. 泰文文本归一化是怎么做的？

**项目实际情况（`rag_llamaindex.py:311` `normalize_thai`，约 150 行注释论证）：**
- **背景**：legacy 泰文语料来自 .docx 转换，存在**两套互不相容的损坏方案**（AB 与 C），同一字符的错法相反，不先判方案就会修错。
- **根因**：转换器把泰文声调符号按 Latin-1 误映射。U+0E4D NIKHAHIT 被映射成 ่ MAI EK（2653 处）、U+0E4D+า 的预组合 ำ 被分解（413 处）；U+02DA/U+02D9（度数符号/点号）其实是 SARA AM ำ 的上半部，后面的 า 是下半部。
- **方案判据**（`_thai_scheme_is_c`）：强证据（U+0E4E、度数符号紧邻泰文）直接判 C；弱证据用统计闸——裸 ํ 个数 ≥ 干净声调符（่ ้）个数才判 C。实测建索引粒度（整条 chunk）误判 0.0%，查询侧干净泰文根本不触发本函数。
- **修复规则**（按可靠性排序，合成**一条正则单次遍历**，避免链式 replace 让前条规则的产物干扰后条匹配）：
  1. 显式词表兜底（如 ไฟทอปธอรํา → Phytophthora 正确拼写，通用判据判不对的个例）
  2. 声调符号与上元音顺序颠倒交换（141 处，干净语料中零反例）
  3. 叠写形态 ํ้า → ้ำ；˚+า → ำ；ํา → ำ（AB 方案）或 ่า（C 方案，唯一分叉规则）；裸 ํ → ่/้
  4. 双写声调+า → 声调+ำ（泰文一个音节最多一个声调，干净参照语料 31.7 万字符中双声调 0 次）
- **防护闸**：必须同段落有泰文才生效——否则用户查"25˚C"会被改成"25ำC"。
- **幂等性**：处理后不再有 U+0E4D/0E4E/02DA/02D9，二次调用短路返回；对干净泰文/中/英/马来文零影响。
- **关键认知（代码注释明确写了）**：归一化**只对 BM25 字符级 n-gram 匹配有意义，对 dense 无影响**——bge-small-zh 的 tokenizer 下泰文无论对错都塌缩成 [UNK]，规范化前后 token 数完全相同。
- **消融验证**：`_probe_th_shortq_thnormalize.py` 做 A/B 臂实验（规则开 vs identity），独立归因。
- **已知限制**：方案判据是统计性的，`ํา` 歧义无法完全局部化（同一词形 `ทํา` 在 AB 是 ทำ、在 C 是 ท่า），所以不能在几十字符的碎片上调用本函数。

**面试回答版本：**
"泰文归一化解决的是语料源头损坏问题。我们的泰文知识库来自老 .docx，转换器把声调符号按 Latin-1 错映射了，而且存在两套互不相容的错法——同一个字符在不同文档里错的写法相反。我的做法分三步：第一步判断文本属于哪套损坏方案，用强证据字符加统计比例闸，在索引粒度上实测零误判；第二步按方案套用修复规则，比如度数符号加 า 其实是泰文 ำ 被拆成两半，要拼回去；声调和元音顺序颠倒的要交换。第三步保证工程性质：所有规则合成一条正则单次遍历，优先级靠分支顺序表达；函数幂等，对干净泰文和其他语言零影响；还要防误伤——用户查'25˚C'时度数符号不能被当成损坏字符改掉。一个重要的经验是：这套归一化只对 BM25 的字符匹配有效，对向量检索没用，因为中文 embedding 模型把泰文全打成了 UNK，这个认知直接决定了我们后面泰文策略的走向。"

## Q6. 术语别名扩展是指什么？

**项目实际情况（`rag_llamaindex.py:843-908`）：**
- **动机**：用户说法与文档写法不一致导致漏召回。实测 6 组别名对里 3 组漏召回：Monthong 查不到金枕、Phytophthora 查不到疫霉、soil moisture sensor 查不到土壤湿度传感器；加扩展后修回 2 组（第 3 组是设备名，术语表未收录）。
- **实现**：术语表 `rag_build/glossary.json` 原本是"别名 → 标准名"单向映射（供翻译统一译名用）。查询侧构建**双向别名索引**：同一标准名下所有说法互相打通，任一说法命中即扩展出全组。例：Monthong / Mon Thong / หมอนทอง / Golden Pillow / 金枕 互为别名。
- **匹配策略按字符类型区分**：
  - 含中文/泰文的词条用**子串匹配**（这两种语言无空格词边界）
  - 纯拉丁词条用**词边界匹配**，避免 "D24" 命中 "D240"
  - 长度 <3 的词条跳过（"ke"、"di" 这类短词噪声太大）
  - 匹配前先做泰文归一化，与索引侧保持同一规范
- **✅ 简历口径已核实**：`glossary.json` 共 13 个分类、**330 条别名**，与简历一致。分类分布：cultivation 59、postharvest 39、disease 38、pest 33、phenology 34、variety_malaysia 28、nutrient 28、malay_common 24、variety_thai 17、fruit_identity 11、plant_organ 8、symptom 7、variety_indonesia 4。另有反直觉教训可用于加分：别名覆盖率统计若不剔除榴莲品种词组，92.8% 的"覆盖"实为 1.4%。

**面试回答版本：**
"别名扩展解决的是'同一实体多种写法'的漏召回。比如用户用泰文问 หมอนทอง，文档里写的是 Monthong 或金枕，语义向量对这些跨语言的等价实体不敏感，精确词匹配又对不上，就会漏。我们把翻译用的术语表反向利用起来：原本是别名到标准名的单向映射，我把它按标准名分组，同组所有说法互相打通——查询里命中任何一个，就把整组别名全部加进检索词。实现上有个细节：匹配策略按语言区分，中文泰文没有词边界只能子串匹配，拉丁文必须词边界匹配，否则 D24 会误命中 D240。这项改动修复了实测 6 组别名对中 2 组的漏召回，在术语密集的种植园语料里，这类漏召回恰好集中在核心概念上，所以对 known-item 类查询的收益明显。"

## Q7. 稠密向量和稀疏向量有什么区别？

**项目实际情况：**
- **稠密（dense）**：bge-small-zh-v1.5 产出的低维连续向量（Milvus），按余弦相似度做语义匹配。优点：能吃同义改写（"疫霉病"≈"根腐病病源"）；缺点：对语种敏感——中文单语模型对泰文查询 tokenizer 输出中位 66.7% 是 UNK，139 条泰文查询只剩 13 个不同 token 序列（最大簇 68 条共享同一序列），语义不同的泰文问题余弦相似度精确等于 1.0，**dense 对泰文是纯噪声**。
- **稀疏（sparse）**：本项目的稀疏通路是**内存内 BM25 扫描**（非 Milvus 稀疏向量），词项是自定义多语言 token：拉丁词+数字、中文 2-3 字 gram、泰文 3-4 字符 gram。优点：精确词匹配，专有名词/品种编号/数字零漂移，泰文靠字符 gram 绕开无词边界问题；缺点：不懂语义，措辞不一致就漏。
- **互补关系是本题核心**：dense 管"意思相近"，BM25 管"字面相同"。四语种场景下每条通路的可靠性按语种分层：中/英/马双路都开，泰文只走 BM25（跳过 dense 还省一次 embedding 推理 81-87ms）。
- **一个容易答错的点**：我们的"稀疏"不是 Milvus 的 sparse vector，是应用层自己实现的 BM25——因为要做泰文 3-4 gram这种自定义 tokenization，Milvus 内置分词器做不到。

**面试回答版本：**
"稠密向量是模型学出来的语义表示，匹配的是'意思'，好处是能容忍同义改写，坏处是它只在训练语料覆盖的语言上可靠——我们用的中文 embedding 对泰文查询 66.7% 的 token 是 UNK，不同泰文问题的相似度算出来全是 1，dense 直接变噪声源。稀疏向量是词频统计表示，匹配的是'字面'，精确词、编号、品种名零漂移，而且 tokenization 可以自己做——我们把泰文切成 3-4 字符的 gram，绕开了它没有空格词边界的问题。两者是互补关系：语义检索抓改写，词法检索抓精确术语。工程上还有个收益：按语种分档后，泰文查询直接跳过 dense，因为那一路只会把 BM25 的正确结果挤出 top-k，跳过还省一次 embedding 推理。"

## Q8. BM25 算法是什么？有什么参数？

**项目实际情况（`rag_llamaindex.py:1024` `_bm25_retrieve`，自实现）：**
- **公式**：`score = Σ IDF(term) × tf×(k1+1) / (tf + k1×(1−b+b×dl/avgdl))`，IDF 用非负变体 `log(1 + (N−df+0.5)/(df+0.5))`。
- **两个核心参数**：
  - `k1 = 1.5`：词频饱和度。控制一个词重复出现时收益递减的速度；k1 越大高词频加分越多。取的是标准默认值，未调参。
  - `b = 0.75`：文档长度归一化强度。0 = 不管长度，1 = 完全按长度惩罚；0.75 是标准值。
- **工程要点（比参数更值得说）**：
  1. 没用 Milvus/Elasticsearch 内置 BM25，应用层自实现——因为 tokenization 必须自定义：拉丁词+数字、中文 2-3 gram、**泰文 3-4 gram**（泰文一个音节占 3-4 字符，用中文的 2-3 gram 会把单音节切碎）。泰文此前根本不在任何分词正则里，BM25 通路对泰文完全空转，这是被评估集抓出来的。
  2. 实现是内存全量扫描：先一遍统计 df，再对命中 node 评分，语料规模（数千 chunk）下毫秒级，省掉一个外部引擎的运维成本。
  3. 查询词经过清洗：去寒暄模板、停用词过滤、泰文归一化与索引侧同一规范。

**面试回答版本：**
"BM25 是词频加逆文档频率的经典词法排序算法：一个词在当前文档出现越多、而在全局越稀有，这篇文档分越高。两个参数：k1 控制词频饱和，出现十次不会是出现一次的十分之一收益，k1=1.5 是标准值；b 控制长文档惩罚强度，b=0.75 平衡长短文档。我们没有用现成引擎而是自己实现了内存版 BM25，原因在 tokenization：种植园语料是中英马泰四语，泰文没有空格分词，而且一个音节占 3 到 4 个字符，我们按语种定制了 n-gram 策略——泰文用 3-4 gram，中文用 2-3 gram——现成引擎的分词器做不到这个。参数本身没调，因为标准值在我们语料上已接近最优，收益大的地方在分词和归一化，不在那两个超参。"

## Q9. RRF 的参数有哪些，如何配置的？

**项目实际情况（`rag_llamaindex.py:1180` `_hybrid_retrieve`）：**
- **RRF 公式**：`hybrid_score = Σ weight_c / (k + rank_c)`，每条通路的候选按排名贡献分数，只看名次不看原始分（避免 dense 余弦分和 BM25 分不可通约的问题）。
- **参数配置**：
  1. `rrf_constant = 60`：标准值，平滑不同排名间的分差——rank 1 和 rank 10 的贡献差被压到 60/(60+1) vs 60/(60+70) 约 2.1 倍。
  2. **通路权重**：dense 1.0，BM25 1.0；但 **exact_mode（精确事实/数据类提问）下 BM25 权重提到 1.35**——这类问题答案必须字面精确，词法通路更可信。
  3. `candidate_limit = max(36, top_k × 8)`：每路召回的候选池深度。
- **三个比参数更重要的工程决策**：
  1. **merge key 用归一化文本而非 node_id 去重**（`_normalized_dedupe_key`）。踩过的坑：如果 dense 侧和 BM25 侧的 node 文本不一致（比如一侧做了泰文归一化另一侧没做），同一个 node 会裂成两条候选、RRF 分数被劈开而掉出 Top-K——所以两侧必须在同一处做同样的 `normalize_thai`。
  2. **泰文查询整条 dense 通路跳过**而非降权：泰文下 dense 是纯噪声却占 1.0 权重，会把 BM25 正确结果挤出 top-k；实测跳过 ns@3 22.3%→30.9%（McNemar p=0.0018），且省 81-87ms embedding 推理。但对外沟通要收敛到 ~+3pp（收益集中在近重复子集）。
  3. **融合后还有证据门控**：非 exact 模式要求候选通过 `evidence_matches_query`（词项覆盖）或 `bm25_score > 1.2` 才进入结果；exact 模式做相邻文本扩展并要求锚点覆盖率 ≥0.6。

**面试回答版本：**
"RRF 的思想是用排名代替原始分数做融合，因为余弦分和 BM25 分不在一个量纲上。参数就两个层面：融合常数 k=60 是标准值，作用是平滑排名间的分差，让榜首和中游不至于差太远；通路权重我们默认各 1.0，但精确提问模式下把 BM25 权重提到 1.35，因为问具体数字、具体条文时字面匹配更可信。真正花功夫的是三个工程决策：第一，去重键用归一化文本而不是 node id，否则两侧文本稍有差异，同一条候选会裂成两条，RRF 分数被劈开直接掉出 top-k，这个坑是我们从 Hit 指标异常反推出来的；第二，按语种决定通路开关，泰文查询直接跳过 dense，因为中文 embedding 对泰文是纯噪声，留着它只会稀释 BM25 的结果，实测显著性检验通过；第三，融合完还有一层证据门控，防止只靠排名混进来的弱相关候选污染生成。我的体会是：RRF 本身没什么好调的，价值在融合之前每条通路是不是干净的。"

## Q11. 评估流水线如何构建的？

**项目实际情况（`rag_eval.py` + `_probe_*.py` 探针族 + report JSON 存档）：**
- **核心设计 1：锚点匹配而非 ID 匹配**。金标里的 doc_id 是旧分片文件的行号指针，重新分片后必然失效；用"来源文本锚点是否出现在召回内容中"做判据，跨分片方案稳定，是 before/after 可比的前提。
- **核心设计 2：多口径分离**（教训驱动）：
  - 主口径：全量证据上的 Hit@1/3/5、MRR。
  - 无泄漏口径（ns）：排除自命中——实测英文 FAQ 题 top1 100% 是问题原文自命中，Hit@3 虚高到 100%，不看这个口径会得出荒谬结论。
  - 知识库口径（kb）：排除所有 FAQ 证据，只看文档类来源；FAQ 占比过高的题 kb 口径无意义（残渣口径不解读）。
- **核心设计 3：分层报告**。按题型/难度分桶，防止整体均值掩盖"数值类问题崩掉"这类局部失效；负向指标（自命中数、证据质量）与正向指标并列输出。
- **工程化**：CLI 子命令 `baseline` / `compare`，每次改动落一份 report JSON 存档（before_rechunk、after_rechunk、after_th_norm、after_skipdense、after_th_bilingual……可完整回放每次改动的收益）；单点改动配独立探针脚本（`_probe_*.py`）做 A/B 臂消融，配对变化用 McNemar 检验报 p 值。
- **方法论**：任何指标异动先怀疑指标本身再怀疑改动；对外报数收敛到合理预期（如泰文跳 dense 的 +8.6pp 收益集中在近重复子集，对外说 ~+3pp）。

**面试回答版本：**
"流水线三件事：判据、口径、流程。判据上用文本锚点而不是文档 ID——因为分块方案一改 ID 全失效，锚点匹配让改前改后可比。口径上做了三套分离：主口径之外加了无泄漏口径，因为我们发现 FAQ 题的 top1 是问题原文自己，Hit@3 虚高到 100%，不看这个口径会得出荒谬结论；还有只看知识库文档的口径，防止 FAQ 证据掩盖文档检索的真实水平。流程上每次改动跑 baseline 加 compare，报告按题型分桶、连同 JSON 存档，所以十二轮迭代每次改动的收益都能回放；关键改动另外写独立探针做消融，配对显著性用 McNemar 检验。这套流水线最大的价值是让我们敢做激进改动——泰文归一化、跳过 dense 这些策略都是它验证出来的。"

## Q12. known-item 是什么？

**项目实际情况（`_probe_th_knownitem_*.py`）：**
- **定义**：known-item search（已知项检索）是信息检索的标准评测范式——给定一段"已知存在的文本"，检验检索系统能否找回它的来源。与 FAQ 金标的区别：FAQ 测"问题→答案"，known-item 测"文本片段→出处"。
- **为什么必须建它**：139 条泰文金标 origin 全是 FAQ、ref_source_file 全为 None，证据 100% 落在 146 个泰文 FAQ node 上。所以"把 651 条 legacy 泰文原文拼进索引"这类针对**正文语料**的改动，在现有金标上**结构性地测不出收益**——金标的检索目标根本不在那里。known-item 用纯机械方式构造了一个能度量的集合。
- **构造方式（无 LLM、无翻译、可复现）**：对每条 legacy 泰文 chunk 的 500 字符原文——查询取前半段中"泰文实词最密集的 60 字符连续片段"，锚点取后半段（`extract_anchors` 提取 24 字符窗口）。查询与锚点物理不重叠，不会退化成平凡自匹配。
- **测出的结果**：泰文双语拼接改动的 known-item Hit@3 从 0.6% 提到 94.5%（简历口径 <1% → 94%）。马来文 known-item 集同理另建（`_probe_ms_knownitem.py`）。
- **方法论价值**：当指标测不出改动收益时，先判断是"改动无效"还是"金标结构上看不到"，后者要构造新判据而不是放弃改动。

**面试回答版本：**
"known-item 是信息检索里的已知项检索范式：拿一段已知存在于语料中的原文当查询，看系统能不能把它所在的原文找回，锚点和查询物理取自原文的不同半段，避免平凡自匹配。我们必须建这个集，是因为发现一个结构性盲区：泰文金标的检索目标 100% 落在 FAQ 上，所以针对泰文正文语料做的任何优化，在原金标上永远测不出收益——不是改动无效，是仪器看不见。known-item 就是为正文语料专造的仪器，它测出泰文双语拼接把 Hit@3 从 0.6% 拉到 94.5%，这个改动用原金标评估收益是零，差点被否掉。这也是我后来反复用的方法论：指标异常时，先分清是系统坏了还是仪器坏了。"

## Q13. 上下文管理中，滑动窗口多大？

**项目实际情况（三层，不止一个数）：**
1. **消息数窗口**：`max_memory_messages = 12`（环境变量 `DURIAN_LANGGRAPH_MEMORY_MESSAGES` 可调）——checkpoint 里只保留最近 12 条消息，更早的用 `RemoveMessage` 物理删除（`durian_langgraph.py:1511` `_trim_memory_node`）；同时 `max_topic_memories = 10` 张话题卡片。

3. **摘要长度上限**：rolling_summary 注入截断 1800 字符、总量 2400 字符；单卡片 last_answer_summary 截 520~900 字符；长期记忆取相关度 top 6 条。

## Q14. 摘要如何设计？是 prompt 吗？

**项目实际情况（`durian_langgraph.py:700` `_build_rolling_summary`、`:595` `_build_memory_instruction`）：**
- **摘要本身不是 LLM prompt，是确定性结构抽取**——这是一个主动的架构决策：
  1. 每轮生成后，从该轮构建**上下文卡片**：主话题（main_subject）、用户目标（last_user_query）、关键事实（key_facts，最近 8 条）、结论摘要（last_answer_summary = 剥掉 markdown 的答案正文，截 520~900 字符）。
  2. rolling_summary = 最近 4 张卡片按"主题=…；用户目标=…；关键信息=…；最近结论=…"模板拼装，总量截 2400 字符。全程零 LLM 调用。
- **注入确实靠 prompt**：follow_up 意图时，把工作记忆 JSON（≤1800 字符）和滚动摘要（≤1800 字符）作为 `[Conversation Memory V2]` 段落拼进 system 指令，并显式声明优先级："当前用户问题 > 工作记忆 > 长期记忆 > 知识库资料"，防止模型把助手过去的推测当用户事实。
- **为什么不用 LLM 做摘要**：①每轮省一次推理（延迟+成本）；②确定性——摘要规则可单测、可复现，LLM 摘要每次产出不同，回归困难；③失败面小——LLM 摘要本身可能失败，而它恰好在上下文已经要膨胀的脆弱环节上。**代价**是丢失了"压缩表达能力"（不能改写归并），所以用 key_facts 截断 + 多卡片并排来补偿。
- LLM 出现在另一个位置：上下文路由器（route_context）用带"最近上下文摘要"的 prompt 判断意图——路由可以失败降级，记忆构建不依赖它。

**面试回答版本：**
"摘要不是让模型生成的，是结构化抽取——这是我们权衡后的决策。每轮对话结束，从答案里确定性地产出一张话题卡片：主题、用户目标、关键事实、结论摘要，滚动摘要就是最近四张卡片按模板拼装，全程零推理成本。它确实是通过 system prompt 注入的，而且带显式的优先级声明，防止模型把历史里助手的推测当成用户说过的事实。不用 LLM 做摘要有三个理由：省一次每轮推理；摘要规则可单测可复现，LLM 摘要每次不一样没法回归；更重要的是可靠性——摘要这个环节恰好用在上下文最长、最接近超限的脆弱时刻，让它再依赖一次可能失败的模型调用，等于在最不该失败的环节加风险。代价是压缩能力弱，我们用关键事实截断和卡片并排来补。"

## Q15. 失败降级怎么做的？

**项目实际情况（`durian__inference_api.py:2440` 起三层防线）：**
1. **事前预算装配（`_fit_proxy_budget`）**：发请求前用 vLLM tokenize 接口精确算 input token，按 `max_model_len − input − 64` 算出输出预算；预算不足时按序降级：①从最旧的非系统消息开始逐条删除（保留当前用户消息+紧邻上下文，至少 3 条不删）；②还不够就把系统指令的低优先级中段压缩（最多 8 轮，`_shrink_system_message`）；③仍然 ≤0 才抛出面向用户的友好错误（"请缩短本轮输入"）。tokenize 接口挂了则退化为保守字符估算（中文按字符数、其他按 len/3、每条消息 +8）。
2. **事中 400 解析重试（`_retry_output_tokens_from_400`）**：万一还是撞上 vLLM 的 400（上下文超限），从错误报文里正则解析出 `maximum context length is N` 和 `prompt contains at least M input tokens`，按 `N − M − 32` 重算 max_tokens 重试一次——不是盲目重试，是带信息量的重试。
3. **组件级降级**：上下文路由器 LLM 调用失败 → 降级为 new_topic（宁可少带历史，也不带错历史污染检索）；生成质量检查器失败 → 启发式兜底响应。原则：任何辅助组件失败都退回保守默认值，不放大为主流程失败。
- 三层与"滑动窗口 + 摘要缓冲"合起来构成简历那条亮点的完整机制（对话成功率 60% → 97%；该数字为业务口径统计，面试时按自己的统计口径说明，如"按天统计的非 5xx 对话完成率"）。

**面试回答版本：**
"失败降级做了三层，核心思想是让超限失败发生在请求发出之前。第一层是事前装配：每次调用前用 vLLM 的 tokenize 接口精确计算这轮的 input token，先算出输出预算够不够，不够就从最旧的非系统消息开始删，删完还不够就压缩系统指令里低优先级的段落，只有连当前问题和必要指令都装不下才报错给用户。第二层是事中兜底：如果仍然撞上 400，我们从错误信息里解析出模型上下文上限和实际 input 数，据此重算 max_tokens 重试一次——是带信息量的重试，不是盲目重试。第三层是组件降级：上下文路由这种辅助 LLM 调用失败时退回保守默认值，比如路由失败就按新话题处理，宁可少带历史也不带错历史。三层合起来，把长会话因 token 膨胀导致的调用失败从主要失败源降成了尾部事件，这是对话成功率从 60% 提到 97% 的机制主体。"

## Q16. 滑动窗口第一层为什么按条数而不是字符数/token 数？

**项目实际情况（`durian_langgraph.py:1511` `_trim_memory_node`）：**
- **根本原因：删除单元决定计数单位**。裁剪动作是 `RemoveMessage(id=...)` 按**整条消息**删除的——add_messages reducer 的删除能力只到消息粒度，不存在"删半个消息"。窗口管的就是"留几条"，所以按条数计。
- **条数层和 token 层的分工不同**：
  1. 条数层保护的是 **checkpoint 本身**（SqliteSaver 落盘体积、每轮 get_state 的恢复成本、前端历史重放的对账成本）——这些成本随消息条数线性涨，与模型无关，模型可以换（vLLM 的 Qwen3 只是当前后端），所以守门标准必须是模型无关的物理量。
  2. token 层保护的是**单次调用的上下文窗口**，只在调用前一刻算才有意义——精确 tokenize 一次要调 tokenizer 接口，而且 input 组成每轮都变，把它放进裁剪层等于每轮白算一次，还可能拿过期数字做决策。
- **消息条数还是"重放对账"的单元**：前端重放历史用 (role, content) 对齐 checkpoint 复用消息 id，单元也是整条消息。
- **一句话总结分工**：条数层是廉价的常数上界（12 条封顶），token 层才是精确预算；前者保证"不失控"，后者保证"不超限"。两层是非对称的——12 条也可能超 token 预算（比如每条都塞了图片），此时靠 token 层兜底。

**面试回答版本：**
"因为第一层裁剪的删除单元就是整条消息——LangGraph 的 RemoveMessage 只能按消息粒度删，先按 token 切再删半个消息没有意义。更重要的是两层分工不同：条数层保护的是 checkpoint 的存储和恢复成本，这部分跟用哪个模型无关，所以用模型无关的物理量做上界；token 层保护的才是单次调用的上下文窗口，它必须用当前模型的 tokenizer 在调用前一刻精确计算，用过期或估算的 token 数做裁剪决策反而危险。所以条数层是廉价的常数上界，token 层是精确预算，非对称兜底——12 条消息如果每条带图片照样可能超限，这时靠 token 层救。"

## Q17. token 窗口限制有多大？为什么要限制？

**项目实际情况（`durian__inference_api.py:2240`）：**
- **数值**：`DURIAN_MAX_MODEL_LEN` 默认 **6144** token（input + output 总预算），vLLM 启动参数 `max_model_len=6144` 同值；安全边距 64，输出偏好 768 / 下限 256。
- **为什么不设大**：
  1. **显存预算**：6144 不是模型架构上限（Qwen3 原生支持更长），是我们给 KV cache 划的每序列上限——vLLM 的 KV cache 显存 = 并发序列数 × 每序列长度，调大 max_model_len 意味着同样显存下并发能力直接缩水，种植园场景多用户同时在线，并发比单序列长度值钱。
  2. **延迟**：attention 计算和 KV 读写随序列长度增长，6144 是在"装得下一轮 RAG 问答（系统指令+证据+历史+输出预算 768）"前提下的收敛值。
  3. **故障域**：上下文越长，长会话越容易逼近上限，失败率越高——6144 的紧预算倒逼摘要/裁剪机制做对，这也是"对话成功率 60%→97%"的机制前提。
- **为什么必须显式限制**：vLLM 超限是硬 400 错误，不预检就会把失败暴露给用户；预检 + 预算装配把失败拦在发出之前。

**面试回答版本：**
"6144 token，这是 vLLM 启动时显式设的 max_model_len，不是模型上限，是我们自己定的预算，原因有三个。第一是显存：KV cache 随并发序列数乘以每序列长度线性涨，把窗口开大同样显存下能同时服务的用户就变少，我们多用户在线场景，并发比单序列长度值钱。第二是延迟：attention 随长度增长，6144 是'装得下一轮 RAG 问答'的最小够用值——系统指令、检索证据、最近 12 条历史、768 的输出预算，刚好。第三是故障域：故意让预算紧一点，倒逼摘要和裁剪机制必须做对，而不是靠大窗口把问题藏起来。并且 vLLM 超限是硬 400，不做事前预算装配的话，失败会直接暴露给用户。"

## Q18. 摘要的结构（主话题/用户目标/关键信息/最近结论）是怎么确定的？

**项目实际情况：**
- **不是先设计后验证，是从失败反推的**。结构演进有明确痕迹（`normalize_context_card` 的 v2 注释）：图片诊断链路里，视觉模型的 label 把上一轮误标成"猫山王/品种口感"，但用户看到的回答实际是病害诊断；用户追问"药物方面"时，旧卡片按 label 走，把追问错误绑定到品种口感——**卡片必须优先尊重上一轮可见回答**。这类 bug 决定了字段清单。
- **每个字段对应一种追问场景的刚需**：
  - 主话题（main_subject）：追问"它怎么治"时用来锚定检索对象——没有它，重建查询找不到主体。
  - 用户目标（last_user_query）：查询重建的原材料。
  - 关键信息（key_facts）：跨多轮保留的事实（检测值、置信度、结论要点），防止中间结论被裁剪掉。
  - 最近结论（last_answer_summary）：可见回答摘要，**优先级最高**——它代表用户实际看到的东西。
  - scenario / category_type（农事 vs 消费；病害/虫害/栽培/品种/品质）：驱动追问话题预置（`followup_topics_for_card`：病害类预置"防治/用药/扩散风险"，品种类预置"口感/甜度/能不能吃"）和冲突修正。
- **字段验证靠真实追问回归**：每个字段的存在都能对应到"没有它时哪类追问会错"。

**面试回答版本：**
"结构不是拍脑袋设计的，是从追问失败的 case 反推的。典型事故：上一轮图片诊断明明说叶片炭疽病，但视觉模型的 label 误标成品种口感，用户追问'用什么药'时，旧卡片按 label 走，把追问绑到了'猫山王口感'上——这个 case 直接塑造了结构：卡片必须有一个'用户实际看到的回答'字段且优先级最高，主题字段必须独立于模型输出的 label、可从可见文本重新提取。剩下的字段各对应一类追问刚需：主话题锚定检索对象，用户目标做查询重建，关键信息让中间结论跨轮存活，场景分类驱动追问话题预置。验证方式就是真实追问的回归集——每个字段都能回答'没有它哪类追问会错'。"

## Q19. 摘要时怎么区分主话题、用户目标这些字段？如何提取的？

**项目实际情况（`durian__inference_api.py:4654` `extract_main_subject_heuristic`、`:4695` `normalize_context_card`）：**
- **概念区分**：
  - **主话题 = 对话"关于什么"**（实体/对象，名词性），用于检索锚定与冲突仲裁。
  - **用户目标 = 用户"想干什么"**（意图+问题原文），用于查询重建。用户目标**不推断，直接抄**——last_user_query 就是用户原话截断，保证不失真。
- **主话题提取是三级级联 + 冲突修正**：
  1. 结构化来源优先：视觉链路的 label、上游结构化卡片已给的 main_subject。
  2. 启发式提取（`extract_main_subject_heuristic`）：先过**品种词表**（猫山王/金枕/D24…），再过**领域正则**（炭疽病、根腐、流胶、黄叶等病虫害/症状模式），都没有则取可见文本第一句/问句（4~40 字符），兜底 40 字符前缀。
  3. **冲突修正（v2 的关键）**：可见回答含明确病虫害/栽培语义（"病害/病斑/杀菌/防治"等关键词命中）而 label 是消费类（品种/口感）时，强制以可见回答为准替换 label 和场景——就是 Q18 那个事故的修复。
- **关键信息（key_facts）提取**：结构化来源直接给（视觉证据拆分，按 ；/换行 split）；文本链路退化成两条：用户问句截 160 字符 + 回答截 220 字符；上限 6 条，进入工作记忆时每条再截 260。
- **最近结论**：答案剥掉 markdown/HTML 注释后截断（520~900 字符），不做语义压缩。
- **取舍说明**：全链路启发式 + 词表 + 正则，无 LLM——与"摘要不用 LLM"同一决策：确定性、可测试、零成本；错误用冲突修正规则兜底而非上模型。

**面试回答版本：**
"概念上主话题是'对话关于什么'，用户目标是'用户想干什么'——后者不推断，直接抄用户原话，保证重建查询不失真。主话题的提取是三级级联：先信结构化来源，比如图片诊断的 label；没有就启发式提取，先过品种词表再过病虫害领域正则，都命中不了就取可见文本第一句。最关键的是第三级冲突修正：如果可见回答里明确出现了病害、防治这类词，而 label 却是品种口感这类消费语义，强制以可见回答为准——这是真实事故修出来的：上一轮明明诊断叶部炭疽病，label 却是猫山王，用户追问用药时被绑到口感上。提取全程用词表、正则、级联规则，不上 LLM，和摘要本身的取舍一致：这个环节要的是确定性和可回归测试。"

## Q20. 什么是"输出偏好"？为什么是 768？

**项目实际情况（`durian__inference_api.py:2450-2463`）：**
- **定义**：preferred_output 是**预算装配循环的停手目标**——裁剪历史消息删到"输出预算 ≥ 768"就停手，不为凑更高输出预算继续牺牲历史。注意它不是生成长度上限：真正发给 vLLM 的 max_tokens = min(请求值, 可用预算)，短会话下可用充足，实际可到 2048。
- **完整的输出预算是三级阶梯**（每级都有独立职责）：
  1. **2048 = 请求上限**（`DURIAN_DEFAULT_MAX_NEW_TOKENS` 默认 2048，`DURIAN_HARD_OUTPUT_CAP` 硬顶 2048）——用户/场景能要的最大值。
  2. **768 = 偏好目标**（`DURIAN_PROXY_PREFERRED_OUTPUT_TOKENS`）——裁剪历史的触发线：可用预算 ≥ 768 时不动历史；< 768 才开始删最旧的非系统消息（保留当前轮+紧邻上下文，最少 3 条不删）。
  3. **256 = 保底告警线**（`DURIAN_PROXY_MIN_OUTPUT_TOKENS`）——裁剪到极致后仍 < 256，记 warning（输出会被截断），< 0 才报错给用户。
- **为什么是 768**：
  1. **装得下一份完整答案**：Qwen tokenizer 中文约 1 token ≈ 1~1.5 字，768 token ≈ 600~1000 字——我们的 prompt 档位本来就约束答案精炼结构化（结论+操作步骤+风险提示），768 是"完整结构化答案"的典型长度上限。代码里其他场景的 max_new_tokens 也佐证：图片最终回答 768、精简链路 800、路由器 96~240。
  2. **失败代价不对称**：输出预算不足的失败是**可见的**（答案中途截断），历史被裁的代价是**不可见的**（但有摘要兜底、可恢复）。所以宁可多裁历史也要保住完整答案的空间——768 定在"完整答案"而非"最低可读"。
  3. **和 6144 总预算咬合**：6144 − 64 安全边距 − 768 输出 ≈ 5300 token 留给 input（系统指令 + 检索证据 + 12 条历史），四个数是一组联动设计。
  4. **延迟**：生成时间随输出 token 线性走，768 是 p95 延迟可接受的经验值；三个值全部环境变量可调，768 是默认而非硬编码。

**面试回答版本：**
"输出偏好是预算装配循环的停手线，不是生成长度上限——裁剪历史消息删到'输出预算够 768'就停，不为了更高输出无限牺牲历史。完整的输出设计是三级阶梯：请求上限 2048，偏好目标 768，保底线 256。768 的取值逻辑：一是装得下一份完整答案，中文大概六百到一千字，我们 prompt 本来就约束答案精炼结构化，其他场景的配置也印证了这个量级；二是失败代价不对称——输出不够答案是当着用户的面截断，是可见故障，历史被裁用户感知不到而且有摘要兜底，所以宁可多裁历史也要保完整答案；三是它和 6144 总预算、64 安全边距是一组咬合的数，给 input 留出约 5300 token。三个值都是环境变量，768 是经验默认，不是魔法数。"

# 第二部分：生产工程题（Q21-Q41）

## Q21. 本地 demo 运行正常，但生产环境并发量升高后 Agent 出现 panic，核心原因是什么？

**核心原因（一句话版）：并发把本地串行执行永远触发不了的"非线程安全共享状态"和"资源上限"暴露了。**

**典型根因按概率排序：**
1. **惰性初始化的模块级单例无锁并发读写**。Agent 服务最常见的模式——`_cache = None` + 首次调用时构建——并发下多个请求同时看到 None、同时构建、互相覆盖；构建到一半的对象被另一个线程读到就是 panic。本项目里 `_ALIAS_INDEX`（术语别名索引）、`_build_lexical_node_cache`（BM25 节点缓存）、`_NEIGHBOR_CACHE`（邻接缓存）全是这个模式，靠进程级串行首次访问躲过，并发下必须加锁或预热。
2. **有状态的单连接存储被并发写**。SqliteSaver 这类单连接 checkpoint 存储，多协程并发写同一个 sqlite 连接会锁冲突甚至损坏；本地单用户永远串行，生产多 worker 就炸。
3. **事件循环被同步阻塞**。同步的 LLM/检索调用跑在 async 框架里，或 CPU 密集推理（图片分类）占住 loop，健康检查超时被 K8s 判死并反复重启。
4. **资源句柄耗尽**：fd（每请求开文件/httpx 连接不关）、连接池打满后阻塞队列无界堆积、显存 OOM。
5. **异常逃逸**：协程/线程里的未捕获异常没有兜底，在生产中间件层变成 5xx 或进程崩溃。

**排查路径：** panic 堆栈定位 → 压测复现（本地低并发跑不出来的，用并发压测+延长运行时间）→ race detector / 并发单测 → 检查所有模块级可变状态。

**面试回答版本：**
"核心原因是并发把'非线程安全的共享状态'暴露了。本地 demo 串行执行，生产并发下最典型的是惰性初始化的缓存单例——多个请求同时看到缓存是空的、同时构建、互相覆盖，构建到一半的对象被别的请求读到直接 panic。第二类是单连接存储的并发写，比如 sqlite 的 checkpoint，本地单用户永远是串行的，多个 worker 一上就锁冲突。第三类是事件循环被同步调用阻塞，健康检查超时被反复杀。排查顺序是：先看 panic 堆栈定位到具体对象，然后压测复现，再全局扫一遍模块级可变状态。修复上要么启动时预热消灭惰性初始化，要么加锁，要么把单连接存储换成集中式支持并发的。我在项目里特别警惕这一点，我们的 BM25 缓存、别名索引都是惰性单例，上线前要么预热要么加锁。"

## Q22. Agent 服务在生产环境中最常见的内存泄露类型有哪些？如何排查和修复？

**Agent 特有的泄露类型（按出现频率）：**
1. **无界缓存**：检索缓存、词项统计、邻接缓存只增不删。Agent 的查询分布是长尾的，无 TTL/无上限的 dict 会缓慢吃光内存。
2. **会话状态只增不清**：checkpoint 存储、会话消息 list、话题卡片，thread 永不过期清理，长期运行必然膨胀。
3. **闭包引用大对象**：回调/生成器持有整个会话上下文，流式响应中断后协程挂起不释放。
4. **连接与游标**：sqlite cursor、httpx client 未在 finally 里关闭。
5. **批处理残留**：上传图片、OCR 中间产物、临时索引文件堆积在磁盘/内存。

**排查（从粗到细）：**
1. 容器监控看 RSS 曲线——阶梯式上涨 vs 突刺，区分慢性泄露和单次大分配。
2. Python 用 tracemalloc 分代快照 diff 定位增长最快的分配点；objgraph 看对象类型计数。
3. gc 统计区分"真泄露"（引用持有）和"对象量大"（该清理没清理）。
4. 对照请求日志：泄露速率是否随请求量线性——是则查 per-request 路径上的持有。

**修复：** 缓存统一加 LRU 上限 + TTL + 版本化失效；会话加生命周期（过期 thread 定期归档清理）；资源用 context manager；流式响应加超时强制释放；批处理产物落盘不留内存。

**面试回答版本：**
"Agent 的内存泄露和普通 Web 服务不同，大头不是代码 bug 而是状态管理。最常见三类：一是无界缓存，检索结果、词项统计这类 dict 只增不删，查询是长尾分布的，缓存量必然持续涨；二是会话状态只增不清，checkpoint、消息历史、话题卡片如果 thread 不过期，长期运行一定膨胀；三是流式响应中断后协程挂起，闭包把整个会话上下文持有住不释放。排查先看容器 RSS 曲线区分慢性泄露和突刺，再用 tracemalloc 分代快照 diff 找增长最快的分配点，并对照请求量看泄露是否线性。修复是体系化的：所有缓存必须有 LRU 上限和 TTL，会话必须有生命周期管理加定期归档，资源全部走 context manager，流式响应必须带超时强制释放。"

## Q23. LLM 响应慢导致整个 Agent 链路超时，分层超时的熔断策略是什么？高并发场景下如何解决？

**分层超时（预算自上而下分解）：**
1. **轮级（turn）超时**：一次用户交互的总预算（如 30s），倒推分配给下面每层。
2. **单次 LLM 调用超时**：再拆三层——连接超时、首 token 超时（TTFT，流式下首 token 到了大概率能出完）、总时长超时。路由器/摘要这类辅助调用给短超时（几秒）。
3. **工具/检索超时**：dense/BM25/外部检索各自独立超时。
4. **降级链是超时的伴生设计**：本项目实际实现了这条链——路由 LLM 超时/失败 → 降级为 new_topic（宁可少带历史不带错历史）；RAGFlow 检索失败 → 本地检索 fallback；vLLM 400 → 解析错误信息带信息量重试一次。原则：任何辅助组件失败都退回保守默认值，不放大为主流程失败。

**熔断器：** 对每个外部依赖独立配置——失败率/连续失败数达到阈值就跳闸，期间请求直接走降级不发真实调用；半开状态放少量探测请求，成功则恢复。关键是熔断的粒度是"依赖级"不是"全局"，LLM 网关挂了不应该熔断检索。

**高并发下：**
1. **舱壁隔离**：每个外部依赖独立连接池/信号量，慢依赖不会占光共享线程池拖垮全链路。
2. **重试风暴保护**：重试必须带 jitter 和重试预算（如重试占比超过 10% 就停止重试），否则上游抖动时重试流量放大三倍把系统打死。
3. **fail-fast**：预算装配阶段就判断"这轮已经不可能在时限内完成"，提前降级而不是等到超时。
4. **流式优先**：首 token 返回后再慢慢生成，把用户感知超时和系统超时解耦。

**面试回答版本：**
"超时要按预算自上而下分解：一轮对话有总预算，拆到每次 LLM 调用再拆到连接、首 token、总时长，流式场景首 token 超时最关键，因为它把用户感知和系统资源解耦了。熔断按依赖做粒度，每个外部依赖独立判断失败率，跳闸期间直接走降级链不发真实调用——我们的降级链是路由失败退回新话题、检索失败退本地 fallback，原则是任何辅助组件的失败都退保守默认值，不许放大成主流程失败。高并发下两件事最关键：一是舱壁隔离，每个依赖独立连接池，慢依赖不能占光共享资源；二是重试风暴保护，重试要带 jitter 和重试预算，否则上游一抖动重试流量放大三倍反而打死系统。另外我在项目里体会到一点：最好的降级是发生在请求发出之前的预算预检，把注定超时的请求提前拦下来。"

## Q24. LLM 接口存在限流，生产环境 Agent 链路较长（包含检索工具、多轮推理），如何优化设计以降低 P95 的 RT？

**先诊断 P95 慢在哪：** 分节点打点（路由、检索 dense/BM25、组装、生成 TTFT 和总时长），本项目每轮都有 turn timing 日志。P95 的来源通常不是单点慢而是"串行 LLM 调用次数 × 每次的不确定性"。

**六个手段（按性价比排序）：**
1. **砍掉非必要 LLM 调用**（最大头）。本项目最有效的一个改动：路由规则优先——闲聊、精确提问、泛化追问用正则直判，只有规则不命中才调 LLM 路由。多数请求省一整次 LLM 调用，这直接砍 P95 而不是磨 P50。
2. **并行化**：dense 和 BM25 两路召回并行；路由和长期记忆检索并行；无依赖的工具并发执行。
3. **前缀缓存**：vLLM 的 automatic prefix caching 对 Agent 是天然红利——系统指令、证据前缀在多轮间高度重复，命中即省 prefill 时间。
4. **语义缓存**：高频 FAQ 类问题归一化后精确匹配缓存答案；命中率取决于 query 分布，长尾场景慎用（污染成本高于收益）。
5. **限流侧配合**：客户端 token bucket 主动限速，避免撞上游限流后进重试退避的恶性循环；并发上限 + 排队（优先级队列：交互请求 > 批任务）。
6. **异步化慢路径**：图片诊断这类重操作流式/后台化，先给用户状态事件，别让它阻塞 P95。

**面试回答版本：**
"先分节点打点定位 P95 慢在哪——Agent 链路的 P95 通常不是单点慢，而是串行 LLM 调用次数乘以每次的不确定性。所以第一优先级是砍调用次数：我们路由层规则优先，闲聊、精确提问用正则直判不调模型，多数请求直接省一次 LLM 调用，这是砍 P95 不是磨 P50。第二是并行化，双路召回并行、无依赖工具并发。第三是前缀缓存，Agent 的系统指令和证据前缀在多轮间高度重复，vLLM 的 prefix caching 是天然红利。第四是客户端主动限速加优先级队列，别撞了上游限流再进重试退避的恶性循环。第五是慢路径异步化，图片诊断这种重操作先回状态事件再慢慢算。核心思想：降 P95 靠结构性删减串行依赖，不靠单点调优。"

## Q25. 生产环境中完整的 Agent 缓存体系是什么样的？哪些数据可以缓存，哪些不能？

**按层分（从请求路径由外到内）：**
1. **答案层（语义缓存）**：归一化 query → 完整答案。仅适合高频、事实稳定、无个性化的问题（FAQ 类）。必须有语料版本号参与 key，知识库一改全失效。
2. **生成层（前缀缓存）**：vLLM automatic prefix caching，系统指令 + 证据前缀跨轮复用，省 prefill。对用户透明，Agent 场景命中率天然高。
3. **检索层**：query → evidence 列表（短 TTL + 语料版本 key）；embedding 缓存（同 query 重复向量化在多轮追问场景很常见）。
4. **索引层（进程常驻）**：BM25 词项统计与文档频率（语料版本内恒定，重建索引时失效）、别名索引、邻接缓存——本项目的 `_build_lexical_node_cache` / `_ALIAS_INDEX` / `_NEIGHBOR_CACHE` 都属这层。
5. **模型层**：embedding 模型、分类模型进程常驻预加载，绝不按请求加载。

**可以缓存的判据：** 内容由 (query, 语料版本) 完全决定、无个性化、无时效性、读多写少。

**不能缓存（或必须逐用户/短 TTL）：**
- **个性化生成结果**：带用户记忆、会话上下文的回答——缓存了就是串话事故。
- **权限相关数据**：任何检索结果如果后续要做权限过滤，缓存必须放在过滤之后或 key 带权限身份，否则低权限用户命中高权限用户的缓存就是越权。
- **时效敏感数据**：告警、工单状态、园区实时状态——缓存即撒谎。
- **写操作的响应**：工单创建这类不可缓存，幂等键除外。
- **长尾语义匹配**：模糊匹配的语义缓存错误率高，污染成本大于收益。

**失效策略统一原则：语料/知识版本号作为所有缓存 key 的组成部分，重建索引发新版本号，旧缓存自然淘汰，不做零散的逐条失效。**

**面试回答版本：**
"我按五层来组织：最外层是答案语义缓存，只给高频、事实稳定、无个性化的问题用；然后是生成层的前缀缓存，系统指令和证据前缀跨轮复用，这是 Agent 特有的红利；检索层缓存 query 到证据的映射和 embedding；索引层是 BM25 词项统计、术语别名这类进程常驻数据；模型层预加载。判断能不能缓存就三条：内容是否完全由查询和语料版本决定、有没有个性化、有没有时效性。个性化回答绝对不能缓存，缓存了就是串话；权限相关的数据要么在过滤后缓存要么 key 带身份，否则就是越权；告警工单这类时效数据缓存即撒谎。失效我坚持一个原则：语料版本号进所有缓存 key，重建索引发新版本，旧缓存整体自然淘汰，不做零散逐条失效——零散失效迟早漏。"

（本部分完）

## Q26. 生产环境中 Agent 的 Token 成本持续增长，有哪些降本优化手段？

**先建立成本观测（没有分项统计就没有优化方向）：** 按场景/用户/会话维度拆 input token 和 output token——input 通常占成本大头（长系统指令+证据+历史），而这恰恰是最容易砍的部分。

**四类手段：**
1. **输入侧压缩（收益最大）**：
   - 上下文裁剪：消息窗口 12 条 + RemoveMessage 物理删除，超窗口的对话不进 prompt。
   - 摘要替代原文：滚动摘要 2400 字符封顶，替代无限增长的历史——这是数量级的压缩。
   - 系统指令压缩：预算不足时压缩系统指令低优先级中段（`_shrink_system_message`），而不是砍证据。
   - 证据控制：邻接扩展截断（2600 字符）、证据去重（seen_expanded 按归一化文本去重）、按相关度限量注入。
2. **调用侧删减**：
   - 规则替代 LLM：路由规则优先，多数请求省一次完整调用。
   - 小模型分工：路由器/意图识别这类任务用小输出预算（96~240 token）甚至小模型。
   - 前缀缓存复用：系统前缀命中即省 prefill 成本（对按 token 计费的托管 API 是 prompt caching 折扣，对自建 vLLM 是算力节省）。
3. **输出侧控制**：输出偏好 768 而非放任 2048，prompt 档位约束答案精炼结构化——output token 单价通常是 input 的数倍，控制输出长度性价比很高。
4. **结构性手段**：高频 FAQ 走语义缓存直接命中不进模型；会话级 token 预算和配额。

**面试回答版本：**
"降本先做观测：按场景拆 input 和 output，Agent 的成本大头几乎总在 input——系统指令、检索证据、历史，而这是最可压缩的部分。手段按收益排：第一是输入压缩，历史用摘要替代原文是数量级的节省，我们滚动摘要两千字符封顶，替代无限增长的原始对话；证据注入做去重和截断；预算紧张时压的是系统指令低优先级段落，不砍证据。第二是调用删减，路由规则优先省掉整次 LLM 调用，意图识别这类小任务给小输出预算。第三是输出控制，output 单价通常是 input 的几倍，我们输出偏好定在 768 并用 prompt 约束答案精炼。第四是结构性的：高频 FAQ 语义缓存直接命中不进模型。核心思想：token 成本治理的本质是上下文治理，砍的是冗余不是质量。"

## Q27. 多用户并发场景下，Agent 的会话隔离如何工程化落地？如何避免串会话问题？

**本项目的实际落地（可作答的骨架）：**
1. **thread_id 是会话的唯一钥匙**：LangGraph 的 checkpoint 按 thread_id 隔离，每轮 `get_state(thread_id)` 读出且只读出该会话的完整状态（消息、摘要、话题卡片、工作记忆）。
2. **user_id 从 thread_id 服务端推导**（`_user_id_from_thread`），长期记忆库（sqlite）按 user_id 行级隔离，一个用户的"记住我用马来语"永远不会注入另一个用户的 prompt。
3. **前端重放对账**：浏览器重放最近历史时按 (role, content) 对齐 checkpoint 里的旧消息复用其 id，防止重复追加；当前轮消息 id 用 thread_id + 内容哈希生成，确定且不可碰撞。
4. **消息注入边界**：长期记忆检索带 user_id，检索结果只进该用户的 graph_input。

**避免串会话的工程要点（生产化补全）：**
- **thread_id 必须服务端签发/校验归属**，不信任客户端任意传 id——传别人的 thread_id 就是读别人的会话，这是越权不是 bug。
- **集中式会话存储**：单机 SqliteSaver 在多 worker 下既是性能瓶颈也是一致性风险，生产换 Postgres/Redis checkpoint，会话才能跨实例迁移。
- **请求内全程传递身份上下文**（请求级 contextvar/ThreadLocal，不落全局变量），任何异步回调里取身份都从闭包捕获而不是读全局。
- **串会话的测试**：并发自动化测试——两个身份交替发消息，断言各自收到的上下文只含自己的历史；这是必须有的回归用例。

**面试回答版本：**
"会话隔离我落成了三层钥匙：thread_id 隔离会话状态，checkpoint 按它存取，一轮对话只能读到自己的消息、摘要、话题卡片；user_id 从 thread_id 服务端推导，长期记忆按用户行级隔离，一个用户的记忆永远不会注入别人的 prompt；消息层面做重放对账，前端重放历史时按内容对齐复用消息 id，防止重复和错位。避免串会话最关键的一条：thread_id 必须服务端签发并校验归属，客户端传别人的 thread_id 是越权不是 bug，鉴权层要拦。第二个关键是存储集中化，单机 sqlite 在多 worker 下既瓶颈又危险，换 Postgres 或 Redis 后会话才能跨实例迁移。最后串会话必须有并发回归测试：两个身份交替发消息，断言各自上下文只含自己的历史——这类事故一次都不能有。"

## Q28. 生产环境中出现大量异步任务堆积，如何进行任务队列治理？

**先分诊（堆积原因决定药方）：**
- 消费太慢（下游 LLM/解析能力不足）→ 扩容/提速消费者。
- 流量突增 → 削峰。
- 毒丸任务（个别任务卡死消费者）→ 隔离 + 超时 + DLQ。
- 消费者挂了 → 告警 + 自愈。

**治理框架：**
1. **任务分级 + 优先级队列**：在线交互请求、近线任务（图片诊断）、离线批任务（语料解析、索引重建）三档，资源隔离——批任务绝不允许挤占交互链路（本项目 MinerU 解析、rebuild_index 这类批操作必须与在线服务错峰或独立部署）。
2. **削峰与背压**：队列有界，满了快速拒绝并返回可预期的降级提示，好过无界堆积后雪崩；生产者侧限流。
3. **消费者治理**：并发度对齐下游容量（LLM 限流值）；每个任务有硬超时，卡死任务不拖垮 worker；优雅停机时先摘流量再 drain 队列。
4. **失败处理**：重试带退避和上限，超限进死信队列（DLQ）留人工重放；任务幂等（重试不产生重复副作用）。
5. **可观测与熔断**：队列深度、积压时间（最老任务年龄）、消费速率三指标告警；积压超过阈值自动降级（如暂停低优先级任务、批任务让路）。

**面试回答版本：**
"队列治理先分诊：是消费慢、流量突增、毒丸任务还是消费者挂了，四种堆积药方完全不同。框架上我落五件事：第一，任务分三级——在线交互、近线、离线批任务，资源隔离，像语料解析、索引重建这种批操作绝不允许挤占交互链路，我们要求错峰或独立部署；第二，队列必须有界，满了快速拒绝返回降级提示，好过无界堆积后雪崩；第三，消费者并发度对齐下游 LLM 的限流值，每个任务带硬超时，不让卡死任务拖垮 worker；第四，重试带上限，超限进死信队列人工重放，任务设计成幂等的；第五，监控队列深度、最老任务年龄、消费速率，积压超阈值自动把低优先级任务让路。核心思想：队列不是缓冲池的无限信用卡，它是需要容量管理和降级预案的资源。"

## Q29. 小模型推理能力弱但成本低，大模型准确率高但成本高，如何平衡二者？

**原则：按任务的"能力下限要求"和"错误代价"分配模型，而不是一刀切。**

**四种落地模式：**
1. **静态分工（最常用）**：任务类型决定模型。确定性强的轻任务（意图识别、路由、抽取、分类）用小模型或规则；开放式生成、多步推理、跨语言理解用大模型。本项目的实际分工：路由器输出预算只有 96~240 token（它只需要吐一个 intent 标签）、图像分类用本地 ResNet（毫秒级、零边际成本）、视觉理解用 qwen-vl-max（外部强模型）、生成用本地 vLLM——按能力需求配成本。
2. **级联（cascade）**：先小模型，置信度不够再升级。ResNet 分类置信度高直接出结果，低置信度或矛盾时升级 VLM 复核——小模型当大模型的守门员，多数请求到不了贵的那层。
3. **蒸馏/微调**：高频场景用大模型的输出蒸馏小模型，但前提是有评估集能证明小模型"够用"。
4. **规则兜底**：最便宜的"模型"是规则。本项目路由规则优先，正则能判的不调任何模型。

**关键护栏：每级分工必须用评估集验证。** "小模型不损质量"是实验结论不是假设——我们 1247 条金标跑过才能说规则路由不伤效果。错误代价不对称的任务（权限判断、敏感操作）永远不降级到小模型。

**面试回答版本：**
"平衡的原则是按任务的能力下限和错误代价分配模型，不是一刀切。四种模式：静态分工最常用，路由、抽取、分类这类确定性任务给小模型甚至规则，生成和推理给大模型——我们路由器输出预算只有一百来个 token，它只需要吐一个标签；图像分类用本地 ResNet 毫秒级零边际成本，视觉理解才用外部 VLM。第二种是级联，小模型当守门员，ResNet 置信度高直接出结果，低置信度升级 VLM 复核，多数请求到不了贵的那层。第三种蒸馏。第四种是规则——最便宜的模型是规则，我们路由正则能判的不调任何模型。关键护栏是每级分工必须评估集验证，小模型不损质量是实验结论不是假设；而且错误代价不对称的场景，比如权限判断，永远不降级。"

## Q30. 生产环境中如何做模型调度？

**调度的决策维度：** 任务类型（生成/路由/嵌入/视觉）、语种（本项目泰文 dense 通路关闭就是"按语种调度通路"的实例）、优先级、当前负载、成本预算、依赖健康状态。

**落地的调度架构分层：**
1. **模型注册表**：每个模型的端点、能力标签、成本、上下文上限集中登记。统一 OpenAI 兼容接口是前提（本项目 `DURIAN_OPENAI_BASE_URL` 抽象让本地 vLLM 和外部 API 可互换）。
2. **静态路由表（默认层）**：场景 → 模型的默认映射，覆盖 90% 流量，可预测可审计。
3. **运行时调整（动态层）**：
   - 健康检查 + 熔断：依赖失败率超阈值切备用模型（本项目模式：RAGFlow 失败自动回落本地检索，`fallback_enabled` 开关）。
   - 负载/限流感知：本地 GPU 打满时排队或切外部 API 兜底。
4. **发布治理（安全层）**：模型/提示词变更先过评估集回归再灰度切流；调度决策必须可回滚、可解释（每次调用记录"为什么选了这个模型"）。

**本项目的实际形态：** 本地 vLLM（生成主力）+ qwen-vl-max（外部视觉）+ bge-small-zh（本地嵌入）+ ResNet（本地分类）——按能力 + 成本静态分工，运行时带熔断降级。这是单团队规模的正确形态；更大规模才需要中心化调度服务。

**面试回答版本：**
"模型调度分四层落地。第一层是模型注册表，把端点、能力标签、成本、上下文上限集中登记，前提是统一 OpenAI 兼容接口，本地 vLLM 和外部 API 才可互换。第二层是静态路由表，场景到模型的默认映射，覆盖九成流量，可预测可审计——我们生成走本地 vLLM、视觉走外部 VLM、嵌入和分类走本地小模型，就是按能力和成本的静态分工。第三层是运行时调整，健康检查加熔断，依赖失败率超阈值自动切备用，我们的检索链路就是外部 RAGFlow 失败自动回落本地。第四层是发布治理，模型和提示词的变更必须先过评估集回归再灰度，调度决策要可回滚可解释。核心思想：调度不是越动态越好，静态可审计的默认层加窄口径的动态调整，比全动态稳得多。"

## Q31. 大量检索场景下 RT 升高，面对百万级知识库如何做性能优化？

**前提判断：检索架构随规模换挡。** 本项目数千 chunk 用内存 BM25 + 单机向量索引是正确形态；百万级必须换挡，方案不可平移。

**百万级的分层优化：**
1. **向量侧**：ANN 索引（HNSW/IVF-PQ）替代精确检索，Milvus 集群化 + 分片（本项目已是 Milvus，单机到集群是容量演进）；参数权衡召回率 vs 延迟（ef_search / nprobe 调档）。
2. **词法侧**：内存全量扫描不可扩展（本项目 BM25 是 O(N) 扫描，百万级必须换倒排索引引擎 ES/Milvus sparse）；查询侧倒排天然 O(命中文档数)。
3. **过滤下推与分区裁剪**：语种、文档类型、租户做成 partition/schema 级隔离，检索前先裁剪候选空间（本项目"泰文跳 dense、按语种分档"就是缩小搜索空间的同思路）；权限过滤在召回层用 metadata expr 完成，不取回再过滤。
4. **两阶段检索**：粗召回放大候选（top_k×N）+ 轻量精排（RRF/小 reranker），控制进入排序的候选量——本项目 candidate_limit = max(36, top_k×8) 就是控制候选膨胀的实例。
5. **缓存与预热**：热查询结果缓存（带语料版本 key）、索引常驻内存避免冷启动、embedding 批量化。
6. **读写分离**：索引重建/更新走 offline 构建 + 原子切换（双索引切换），不在线抖动。

**面试回答版本：**
"第一件事是承认架构要随规模换挡：我们几千 chunk 用内存 BM25 加单机向量索引是对的，百万级不可平移。优化分四层：向量侧上 ANN 索引加 Milvus 集群分片，用召回率换延迟，参数可调档；词法侧内存全量扫描必须换成倒排索引引擎，倒排的复杂度是命中文档数而不是全库规模；第三是过滤下推和分区裁剪，语种、文档类型、租户在分区层隔离，检索前先裁剪候选空间，权限过滤用 metadata 表达式在召回层完成——我们泰文跳过 dense 通路、按语种分档，本质就是缩小搜索空间；第四是两阶段检索，粗召回控制候选量再轻量精排，我们的候选池是 top_k 的八倍封顶，防止候选膨胀拖垮排序。再加上热查询缓存和索引离线构建原子切换。核心思想：检索优化是让每一步接触的候选规模可控地小。"


## Q32. Agent 服务如何做启停设计？

**启动设计（核心是"没准备好不接流量"）：**
1. **依赖顺序编排**：存储 → 检索索引/模型 → 后端服务 → 网关。本项目 start_all.sh 的编排顺序就是存储和 vLLM 先行、API 后起。
2. **启动预热**：模型加载、索引构建、缓存填充（BM25 词项统计、别名索引这类惰性单例在启动时构建，同时消灭 Q21 说的并发惰性初始化风险）。
3. **就绪探针与存活探针分离**：readiness 通过才挂到负载均衡接流量；liveness 只判断进程是否死锁。模型加载要几分钟，两者不分离就会被误杀循环。
4. **启动自检**：依赖端点连通性、索引版本一致性（索引与语料版本不匹配要拒绝启动而不是带病服务）。

**停机设计（核心是"在途请求善终"）：**
1. 收到 SIGTERM → 先从负载均衡摘除（停止接新请求）。
2. Drain 在途请求（带硬超时，本项目每轮有 turn timing，drain 上限可据此设定）。
3. 释放资源：关闭存储连接、flush 日志、checkpoint 落盘。
4. 超时强杀兜底。
5. **批任务/后台线程要有取消点和 checkpoint**，停机时能记录进度下次续跑（衔接 Q34）。

**面试回答版本：**
"启停设计的核心各一句话：启动是'没准备好不接流量'，停机是'在途请求善终'。启动侧做依赖顺序编排——存储、模型、索引先起，后端后起，网关最后挂；启动时预热索引和缓存，把惰性初始化消灭在低并发时刻；就绪探针和存活探针必须分离，模型加载要好几分钟，不分离就会被反复误杀。停机侧收到信号先摘流量，再 drain 在途请求——drain 上限按我们的轮耗时数据设定，然后释放资源落盘 checkpoint，超时强杀兜底。还有一点容易被忽略：后台任务要有取消点和进度记录，停机时能优雅停下，下次续跑而不是从头来。"

## Q33. 如何避免发布期间导致用户体验报错？

**发布策略组合：**
1. **蓝绿/滚动发布 + 就绪探针门控**：新实例 ready 才接流量， unhealthy 自动摘除——基础中的基础。
2. **灰度发布**：按流量比例或用户分组逐步放量，观察核心指标（成功率、P95、降级触发率）再全量。
3. **优雅排空**：老实例摘流量后 drain 在途长连接（SSE 流式对话尤其重要，直接断就是用户可见的报错）。
4. **状态与 Schema 兼容**——Agent 特有的坑：
   - 会话状态（checkpoint/state 字段）演进必须向后兼容，老会话在新代码上要能继续，否则存量用户全部断线。
   - 索引与语料版本对齐发布（先建新索引再切读，双索引原子切换）。
   - prompt/模型变更先过评估集回归，防止"发布成功但质量崩了"这种不报错的事故。
5. **前端配合**：请求自动重试 + 会话恢复（重试携带 thread_id，服务端从 checkpoint 恢复上下文，用户无感迁移）。
6. **回滚预案**：发布即回滚演练，配置和索引都保留上一版本（本项目的 storage 备份习惯就是这个模式）。

**面试回答版本：**
"分四层防。第一层是发布策略本身：滚动加就绪探针门控，新实例不 ready 不接流量，再加灰度按比例放量观察核心指标。第二层是优雅排空，流式对话的长连接必须 drain 完，直接断就是用户可见报错。第三层是 Agent 特有的兼容性：会话状态的 schema 演进必须向后兼容，老会话要能在新代码上继续，否则存量用户全体断线；索引和语料版本要对齐发布，先建新索引再原子切读；prompt 和模型变更先过评估集回归——发布成功但质量崩了，比报错更隐蔽更严重。第四层是用户体验兜底：前端自动重试带 thread_id，服务端从 checkpoint 恢复上下文，实例迁移对用户无感。回滚预案要和发布一起做，配置和索引都留上一版本。"

## Q34. 生产环境中如何解决 Agent 长任务执行失败后需要从头运行的问题？

**核心机制：checkpoint + 断点续跑 + 幂等。**

1. **框架级 checkpoint（本项目已内建）**：LangGraph 的图执行每节点完成后状态落盘（SqliteSaver），进程崩溃后 `get_state(thread_id)` 恢复完整状态从断点继续——这就是我们长会话跨重启不丢的机制，同样适用于长任务。
2. **任务级状态机**：长任务拆成显式步骤（解析 → 清洗 → 索引 → 评估），每步：
   - 幂等（重跑不产生重复副作用——入库用 upsert，文件写临时名再原子改名）；
   - 进度落盘（任务表记录步骤状态与产物指针）；
   - 失败从失败步重跑，前置步骤的产物直接复用。
3. **重试策略**：区分瞬时错误（可重试，带退避）和确定性错误（重试无意义，进 DLQ 人工处理）；重试预算防风暴。
4. **补偿设计（涉及外部副作用的任务）**：工单创建这类写操作失败后，恢复逻辑要判断"上次是否已创建成功"（幂等键查重），不能盲目重放造成重复工单。
5. **产物版本化**：中间产物带版本号落盘（本项目的 chunks_cache、clean_chunks 就是这种中间产物），重建只跑受影响的下游步骤。

**面试回答版本：**
"三个关键词：checkpoint、断点续跑、幂等。框架层面 LangGraph 每个节点执行完就落盘状态，进程挂了从断点恢复，这是我们长会话跨重启不丢的同一套机制。任务层面把长任务拆成显式步骤的状态机，每步设计成幂等——入库用 upsert、文件写临时名原子改名——进度和产物指针落任务表，失败从失败步重跑而不是从头。重试要区分瞬时错误和确定性错误，后者重试无意义进死信队列。最容易被忽略的是外部副作用的补偿：工单创建失败恢复时必须先用幂等键查'上次是否已建成功'，盲目重放就是重复工单。中间产物全部版本化落盘，重建只跑受影响的下游。"

## Q35. Agent 工程中哪些逻辑必须通过工程化硬编码解决，不能交给 LLM 自主判断？

**判据：错误代价高、必须可审计、必须确定性的逻辑，硬编码；语义模糊、需要泛化的，交给 LLM 但有规则兜底。**

**必须硬编码的清单（全部有本项目实例）：**
1. **权限与安全**：工具白名单、敏感操作二次校验、角色注入——LLM 可被 prompt 注入诱导绕过，安全边界必须是代码边界。
2. **敏感信息闸门**：密码/token 类内容拒入长期记忆（`_MEMORY_SENSITIVE_MARKERS`）——不能指望模型"自觉不记"。
3. **上下文预算与裁剪**：超限是硬错误，裁剪顺序（先历史后系统指令再报错）是确定性代码——让模型自己"看着办省着点用"必然超限。
4. **路由的确定性底线**：规则优先、LLM 兜底；LLM 路由失败降级到 new_topic 而不是让模型猜。
5. **数据一致性约束**：检索两侧的归一化必须代码保证一致（dense 与 BM25 侧同一 `normalize_thai`，否则 RRF 去重键裂开）；索引与查询侧的规范对齐不能靠模型。
6. **仲裁规则**：上下文卡片冲突修正（可见回答优先于视觉 label）——用代码裁决，因为它是从事故修出来的确定性规则。
7. **记忆优先级与使用边界**：system 声明"用户问题 > 工作记忆 > 长期记忆 > 知识库"、"不得把助手推测当用户事实"——方向靠声明，执行靠工程结构（分层注入）。

**反例（应该交给 LLM 的）**：意图理解的模糊地带、答案的组织与措辞、跨语言表达、追问的语义补全——这些硬编码反而脆。

**面试回答版本：**
"我的判据是三条：错误代价高不高、要不要可审计、需不需要确定性。命中任何一条就硬编码。具体清单：第一是权限和安全——工具白名单、敏感操作二次确认必须是代码边界，因为模型可以被注入诱导绕过；第二是敏感信息闸门，密码 token 拒入记忆，不能指望模型自觉；第三是上下文预算，超限是硬错误，裁剪顺序必须确定性，让模型自己省着用必然超限；第四是路由底线，规则优先模型兜底，模型失败降级到保守默认而不是让它猜；第五是一致性约束，比如我们检索两侧的泰文归一化必须代码保证同规范，差一点融合去重就裂开。反过来说，意图的模糊地带、答案组织、跨语言表达该给模型，硬编码反而脆。一句话：LLM 负责语义，工程负责边界。"

## Q36. 生产环境中如何评估 Agent 的性能、成本和稳定性？核心观测指标有哪些？

**三大维度 + 质量第四维：**

**性能：**
- TTFT（首 token 延迟）——流式场景的用户体验主指标
- 整轮 RT 的 P50/P95/P99（不是均值——长尾才是投诉来源）
- 分节点耗时：路由、dense 检索、BM25 检索、生成（本项目每轮 turn timing 日志已具备：total、events 数、分阶段 status 事件）
- 队列深度 / 排队时间

**成本：**
- token in/out 按场景、用户、会话维度分账
- embedding 调用数与费用、外部 API 调用数（视觉模型）
- 缓存命中率（命中率即省下的钱）
- 单次成功对话的完全成本（cost per resolved conversation）

**稳定性：**
- 对话完成率（非 5xx、非超时的完成比例——简历 60%→97% 的口径）
- 降级触发率分层统计：路由降级次数、400 重试次数、fallback 命中次数（降级是正常运转的一部分，但要监控它的频率趋势——突增说明上游有问题）
- 重试率、超时率、熔断器状态
- 资源面：GPU 利用率/显存、RSS、连接池饱和度
- 会话续存率（发布/重启后会话能恢复的比例）

**质量（Agent 特有，防'指标全绿体验崩了'）：**
- 检索质量回归：Hit@K 定期跑金标（本项目 1247 条评估集 + report 存档机制）
- 证据质量分布、用户负反馈率、澄清请求率

**落地形态：** 结构化日志（每轮一条含全链路 span 的记录）→ 指标聚合 → 按上表建看板，告警分级（完成率/RT 突降是 P0，降级率缓涨是 P1）。

**面试回答版本：**
"我按四个维度建指标。性能看 TTFT 和整轮 RT 的分位数——P95 不是均值，长尾才是投诉来源；还要分节点打点，我们每轮日志里有路由、检索、生成的分段耗时。成本按场景和用户分账 token 进出，加 embedding 和外部 API 调用数，缓存命中率也要看，它就是省下的钱。稳定性最核心的是对话完成率，我们把它从 60% 做到 97%；特别要监控降级触发率的分层统计——降级是设计内的正常运转，但频率突增说明上游出问题了。第四个维度是质量，Agent 特有的坑是指标全绿但体验崩了：检索 Hit@K 要定期跑金标回归，我们 1247 条评估集加报告存档就是这个用途。告警分级：完成率和 RT 突降是 P0，降级率缓涨是 P1。"

## Q37. Agent 批量处理任务时 CPU 和内存瞬间打满，这类问题如何解决？

**根因几乎总是：无界并行 + 全量物化。** 批处理把 N 个任务同时发起（CPU 打满），每个任务又把全量数据加载进内存（内存打满）。

**解决（按层次）：**
1. **限并发**：工作池/信号量把并行度钉在资源预算内（CPU 核数或 LLM 限流值，取小者）——最直接有效。
2. **流式处理替代全量物化**：生成器逐条处理，不 `list()` 全量；中间产物落盘（JSONL 逐行写）不驻留内存——本项目 clean_chunks.jsonl、chunks_cache.jsonl 的逐行 JSONL 形态就是这种设计。
3. **分批 + 断点**：大批任务切片，每片完成即释放；片级进度落盘支持续跑（衔接 Q34）。
4. **资源隔离**：批处理与在线服务分开部署或容器资源限制（cgroup/K8s limit），批任务打满自己不打满在线链路；错峰执行（夜间窗口）。
5. **降载处理**：输入先降采样——图片先缩放再推理（视觉模型对大图是平方级开销）、OCR 按页粒度处理。
6. **背压**：队列有界，生产快于消费时阻塞或延迟生产，而不是堆积。

**面试回答版本：**
"根因几乎总是两个词：无界并行加全量物化——N 个任务同时发起把 CPU 打满，每个任务又把全量数据读进内存。解法按层次：第一限并发，工作池把并行度钉死在资源预算内，取 CPU 核数和下游限流值的较小者；第二用流式替代物化，生成器逐条过，中间产物逐行落 JSONL 不驻留内存，我们的语料清洗管线就是这个形态；第三分批加断点，每片完成即释放资源；第四资源隔离，批处理和在线服务分开部署或容器限额，再错峰到夜间窗口——批任务打满自己可以，打满在线链路不行；第五输入降采样，图片先缩再推理，大图对视觉模型是平方级开销。最后队列必须有界形成背压，生产快于消费就阻塞生产，而不是无界堆积。"

## Q38. Agent 多轮对话中上下文越来越大、越来越冗余，如何通过工程化治理？

**本项目的完整答案（七件套，全部已实现，可直接背）：**
1. **物理裁剪**：消息窗口 12 条封顶，超出的用 RemoveMessage 物理删除——不是"不发给模型"，是从 checkpoint 里删掉，存储也不膨胀。
2. **摘要续命**：被删对话的信息进滚动摘要（最近 4 张话题卡片、2400 字符封顶）+ 话题卡片，下一轮以 system 指令段注入——信息以 O(1) 上界的形式存活。
3. **按意图开关历史**：追问才注入历史与摘要；识别为新话题/精确提问时主动切断——上轮的病名、园区名不允许串进本轮检索。冗余治理不只是压缩，还有"该断就断"。
4. **查询重建替代带全史**：泛化追问（"再详细点"）不把历史塞给模型，而是重建出一条带主题的完整查询——把多轮问题化归为单轮。
5. **注入去重与限量**：长期记忆只取相关 top 6；工作记忆/摘要各 1800 字符封顶；证据去重（归一化文本键）。
6. **卡片级去重合并**：同 context_id 的话题卡片原位替换（`_merge_topic_memories`），同话题追问不产生重复卡片；卡片各字段截断（key_facts 6 条、每条 260 字符）。
7. **系统指令也能压**：预算紧张时压缩系统指令低优先级中段，压缩优先级明确（历史 > 系统指令装饰段 > 证据 > 当前问题）。

**治理原则总结：** 上下文不是越多越好——无关历史是噪声，会稀释注意力并引发串扰；治理目标是"每轮注入的信息密度恒定"，而不是"尽量多保留"。

**面试回答版本：**
"我们落了七件事：物理裁剪，消息十二条封顶，超出的从 checkpoint 里物理删除，存储也不膨胀；摘要续命，被删的信息以话题卡片和滚动摘要的形式存活，总量两千字符封顶，是 O(1) 上界；按意图开关历史，追问才带历史，新话题主动切断——上轮的实体不许串进本轮；查询重建，'再详细点'这种追问不靠带全史，而是重建出带主题的完整查询，把多轮化归成单轮；注入去重限量，长期记忆取 top 6，各段有字符上限；卡片同话题原位合并不重复累积；最后系统指令的装饰段在预算紧张时也可压。核心认知是：上下文不是越多越好，无关历史是噪声，会稀释注意力引发串扰。治理目标是每轮注入的信息密度恒定，不是尽量多保留。"

## Q39. 第三方 LLM 接口不稳定、存在抖动、超时和报错，如何保证 Agent 系统高可用？

**原则：把外部依赖当"随时会挂"设计，高可用来自冗余 + 隔离 + 降级，不来自祈祷 SLA。**

**手段分层：**
1. **多端点冗余**：主备模型/多供应商，统一 OpenAI 兼容接口让切换成本接近零（本项目 `DURIAN_OPENAI_BASE_URL` 抽象：本地 vLLM 与外部 API 可互换；结构上"本地为主 + 外部为辅"，本地兜得住外部抖动）。
2. **超时与重试纪律**：连接/首 token/总时长分层超时；重试带退避 + jitter + 上限 + 重试预算，只重试幂等的瞬时错误（429/超时），不重试 400 类确定性错误——但要做带信息量的处理（本项目从 400 报文解析上下文上限重算参数重试就是实例）。
3. **熔断器**：按依赖独立熔断，跳闸期间直接走降级不发调用，半开探测恢复。
4. **舱壁隔离**：外部调用独立连接池/信号量，外部抖动不许占光共享资源拖垮本地链路。
5. **降级链（质量阶梯）**：外部强模型失败 → 本地小模型 → 模板化保守回复。宁可答案保守，不可链路 5xx。
6. **缓存兜底**：高频问答缓存命中则完全不触碰外部。
7. **快速开关**：配置中心可一键切换端点/关闭外部依赖（本项目 `fallback_enabled` 类开关模式），不等发布。
8. **可观测**：按依赖维度看错误率/延迟/熔断状态，抖动趋势提前发现。

**面试回答版本：**
"原则是把外部依赖当成随时会挂的东西来设计，高可用来自冗余、隔离、降级三件套。冗余是多端点主备，统一 OpenAI 兼容接口让切换成本接近零，我们的结构是本地模型为主外部 API 为辅，本地兜得住外部抖动。纪律上是分层超时加重试规则：只重试瞬时错误且带退避和预算，四百类确定性错误不盲目重试，但做带信息量的处理——我们从超限报文里解析出实际上限重算参数重试一次。熔断按依赖独立，跳闸期间直接降级不发调用。舱壁隔离保证外部抖动不占光本地资源。降级链是质量阶梯：外部强模型失败退本地小模型再退模板化保守回复，宁可答案保守不可链路五xx。再加缓存兜底和配置中心一键切换开关。"

## Q40. 企业级 Agent 如何做权限和数据层面的隔离？多租户工程化如何设计落地？

**本项目已沉淀方案（docs/用户级权限隔离方案.md，可直接引用）：**

**身份层（前提）：**
- 角色经 Header 注入 + ThreadLocal 传递——但要清醒：**身份可伪造是这个方案的前提问题**，生产必须换成网关签发的 JWT/token，Header 方案只在内网可信链路成立。

**工具层（能做什么）：**
- 工具白名单按角色注册（一线人员没有工单下发工具的调用权）；
- 敏感操作二次校验（写操作确认）；
- 工具调用全部审计日志。

**数据层（能看什么）：**
- 知识库分片隔离；短期方案检索后过滤（权限标签过滤召回结果），中期演进为 RAGFlow dataset 级映射，长期行级/租户级隔离。
- 会话与记忆按 user_id 行级隔离（thread 归属校验，防止读别人的会话——衔接 Q27）。

**多租户工程化：**
1. **租户标识贯穿全链路**：请求 → 会话 → 记忆 → 检索 → 缓存 key，任何一环丢失租户上下文就是隔离缺口。
2. **检索层隔离下推**：租户/权限做 Milvus partition 或 metadata expr 过滤，在召回层完成，绝不取回后过滤（性能和安全的双赢）。
3. **缓存带身份**：权限相关缓存 key 必须含租户/角色（衔接 Q25，否则就是跨租户数据泄漏）。
4. **越权测试常态化**：用低权限身份跑越权 query 回归集，作为 CI 的一部分——权限是测出来的不是声明出来的。
5. **租户级配额与成本分账**：token、存储、并发按租户限额计量。

**面试回答版本：**
"三层隔离各管一件事。身份层是前提：我们角色走 Header 注入加 ThreadLocal 传递，但要清醒这是内网可信链路的方案，身份可伪造是它的前提问题，生产必须网关签发 token。工具层管'能做什么'：按角色的工具白名单、写操作二次校验、全量审计。数据层管'能看什么'：知识库分片，短期检索后过滤，中期做数据集级映射，长期行级隔离；会话和记忆按用户行级隔离，thread 归属必须校验。多租户工程化我强调四点：租户标识贯穿全链路，请求到缓存 key 任何一环丢了就是缺口；隔离在检索召回层下推完成，用分区和 metadata 过滤，绝不取回再过滤；缓存 key 必须带身份，否则就是跨租户泄漏；越权测试常态化进 CI——权限是测出来的，不是设计文档里声明出来的。"

## Q41. 从零搭建一个生产级可用的企业级 Agent 平台，核心落地的功能顺序是什么？

**顺序背后的两条原则：评估先行（没有仪器之前不做任何"优化"）、闭环优先（先窄后宽，先让一条链路生产可用再铺功能）。**

**落地顺序（结合本项目实际演进路径）：**
1. **最小闭环 + 评估集（同步做）**：单轮 RAG 链路（分块 → 索引 → 检索 → 生成）跑通的同时建金标评估集和 before/after 对比流水线——仪器先于优化。本项目的教训是正面的：1247 条评估集和 report 存档让后面十几轮迭代每步收益可回放。
2. **会话与记忆**：thread checkpoint、多轮上下文、摘要裁剪——多轮是 Agent 价值的分水岭，也是复杂度的主要来源。
3. **可观测性**：结构化日志、分节点耗时、成本分账——在用户变多之前，不是之后。
4. **稳定性**：超时分层、降级链、预算装配、优雅启停——量来之前把失败模式设计好。
5. **权限与隔离**：角色注入、工具白名单、数据分片、越权测试——企业场景这个不过关不能接真实用户。
6. **性能与成本**：缓存、并行、大小模型分工、token 治理——有观测数据后才谈得上优化。
7. **平台化**：任务队列治理、批量能力、多租户配额、发布治理——规模化之后的事。

**为什么这个顺序：** 每一步是下一步的前提——没有评估集就无法验证记忆改动没伤检索；没有可观测就无法定位稳定性问题；没有稳定性就谈不上性能优化。反过来，先铺平台化再做闭环是常见的死法。

**面试回答版本：**
"我的顺序有两条原则：评估先行、闭环优先。第一步是把最小闭环和评估集同步做——单轮 RAG 跑通的同时把金标集和对比流水线建起来，仪器先于优化，我们项目最正确的决策就是这个，后面十几轮迭代每一步收益都能回放。第二步会话与记忆，多轮是 Agent 价值的分水岭。第三步可观测，结构化日志、分节点耗时、成本分账，在用户变多之前做。第四步稳定性，超时、降级、预算装配、优雅启停，把失败模式在量来之前设计好。第五步权限隔离，企业场景不过关不能接真实用户。第六步才是性能与成本优化——有观测数据才谈得上优化。第七步平台化，队列治理、多租户、发布体系。逻辑是每一步是下一步的前提，反过来先铺平台再做闭环，是我见过最常见的死法。"
