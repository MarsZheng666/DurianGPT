# RAG 中表格与图片的向量化方案调研

> 面向 durian-training 项目（LlamaIndex + FAISS + bge-small-zh-v1.5 + RAGFlow，已有 qwen-vl-max 可用）
> 整理日期：2026-09-01

---

## 0. 先明确一件事：为什么不能"直接扔进去"

Embedding 模型（本项目为 `bge-small-zh-v1.5`）的训练语料是**自然语言句子**。它对以下输入基本无能：

- `<table><tr><td>79.59</td><td>182.95</td></tr></table>` —— 裸数字 + 标签噪声，语义向量接近随机
- `image_path: https://cdn.../xxx.jpg` —— 一串哈希文件名，没有任何可检索语义
- 表格被 512 token splitter 从中间切断 —— 表头和数据行分家，命中后模型只能瞎猜

所以表格和图片的向量化，本质是**"把非文本模态翻译成 embedding 模型能理解的文本"**，或者**"换一个能理解该模态的 embedding 模型"**。所有方案都是这两条路的变体。

本项目当前状态：图片 100% 丢弃；表格降级为无表头裸数字（695 个 chunk）；73% chunk 含 MinerU JSON 残渣，22.8% 被噪声过滤器整块丢掉。详见 `rag_llamaindex.py:158-254`、`auto_rag.py:160-242`。

> **重要更正（2026-09-01 核查后）**：本文第 5 节原 P0「重跑 MinerU JSON 的解析」**无法执行** —— 经核查本地、远端 `durian-server` 全盘、RAGFlow dataset 三处，22 篇文献的源 PDF 与 MinerU 原始 JSON 均已丢失，且打平数据被硬截断在 500 字符无法还原。实际执行流程改为「重新采集文献 → 本地 MinerU」，详见 `docs/RAG_表格图片向量化_实施流程.md`。本文其余方案对比部分仍然有效。

## 1. 表格向量化方案

### 方案 T1：结构化转 Markdown / CSV 文本（工业界主流）

把表格转成 Markdown 表格文本，整表作为一个不可分割的 chunk，前面拼上表格标题（caption）和所属章节。

```markdown
【表 3-2 不同榴莲品种果实品质比较】（来源：中国榴莲栽培技术, p.45）

| 品种 | 单果重(g) | 可溶性固形物(%) | 果肉率(%) |
|------|-----------|-----------------|-----------|
| 猫山王 | 1800 | 28.5 | 32.1 |
| 金枕 | 2500 | 24.0 | 30.5 |
```

| 项 | 说明 |
|---|---|
| 优点 | 实现成本最低；保留完整结构；LLM 对 Markdown 表理解极好；可读、可调试、可回显 |
| 缺点 | 大表（>50 行）会超 chunk 上限；纯数字表的向量语义仍然弱 |
| 适用 | 中小规模表格，占实际文档 80%+ |
| 关键实现点 | ①表格**不参与** splitter 切分，整表一个 node；②必须拼接 caption + 上下文段落，这是语义向量的主要来源；③原始 HTML 存 metadata 供前端渲染 |

> 本项目最该先做的就是这个。MinerU 已经把表格识别为 `table` 类型并给出了 HTML（键名为 `spans[].html`），只是在落地时被 `str()` 打平丢掉了。

### 方案 T2：表格摘要 / LLM 生成描述（Summary Indexing）

用 LLM 为每张表生成一段自然语言摘要，**摘要参与向量化，原表参与最终喂给 LLM**（父子索引 / MultiVector Retriever）。

```
摘要（入向量库）：本表比较了猫山王、金枕、青尼等 6 个榴莲品种的单果重、
可溶性固形物含量与果肉率，其中猫山王可溶性固形物最高（28.5%），
金枕单果重最大（2500g）。

原表（存 docstore，检索命中后取出喂 LLM）：| 品种 | 单果重 ... |
```

| 项 | 说明 |
|---|---|
| 优点 | 彻底解决"纯数字表向量语义弱"；用户用自然语言提问（"哪个品种最甜"）也能命中；大表可压缩 |
| 缺点 | 需要一次离线 LLM 调用（成本/时间）；摘要可能失真，是幻觉的潜在来源 |
| 适用 | 数值型表格、指标对比表 —— 恰好是本项目论文类 PDF 的主要表格类型 |
| 框架支持 | LlamaIndex `IndexNode` / `SummaryIndex`；LangChain `MultiVectorRetriever` |

### 方案 T3：行级 / 单元格级切分（Row-level Chunking）

大表按行拆开，每行独立成 chunk，但**每行都复制一份表头**：

```
表 3-2 榴莲品种品质：品种=猫山王，单果重=1800g，可溶性固形物=28.5%，果肉率=32.1%
表 3-2 榴莲品种品质：品种=金枕，单果重=2500g，可溶性固形物=24.0%，果肉率=30.5%
```

| 项 | 说明 |
|---|---|
| 优点 | 精确命中单条记录；天然规避 chunk 长度限制；对"猫山王的果肉率是多少"这类问题召回极准 |
| 缺点 | chunk 数量爆炸；无法回答"哪个最高"这类需要全表视野的聚合问题 |
| 适用 | 长表、名录表、参数表；建议与 T1 **同时**入库（整表 + 行级双写） |

### 方案 T4：Text-to-SQL / 结构化旁路（不走向量）

表格抽出后落进真正的数据库（SQLite/DuckDB），查询时由 LLM 生成 SQL 而非向量检索。

| 项 | 说明 |
|---|---|
| 优点 | 数值计算、排序、聚合 100% 准确，无幻觉 |
| 缺点 | 工程量大；要求表结构规范统一；异构表格难以归一 |
| 适用 | 表结构高度统一的场景（如统一格式的品种登记表）；不适合论文里五花八门的表 |

### 方案 T5：表格截图 + 多模态向量（见 I3 ColPali 路线）

不做结构解析，直接把表格区域截图，用视觉 embedding 检索。适用于跨页合并单元格、复杂嵌套表等 OCR 必败的场景。详见第 2 节 I3。

### 表格方案对比

| 方案 | 实现成本 | 检索精度 | 数值可靠性 | 本项目建议 |
|---|---|---|---|---|
| T1 Markdown 整表 | ★ 低 | 中 | 高 | **必做，第一优先** |
| T2 LLM 摘要+父子索引 | ★★ 中 | 高 | 高 | **推荐，第二步** |
| T3 行级切分 | ★ 低 | 高（点查） | 高 | 可选，与 T1 双写 |
| T4 Text-to-SQL | ★★★★ 高 | 极高 | 极高 | 暂不做 |
| T5 表格截图向量 | ★★★ 中高 | 中 | 低（需 VLM 读数） | 仅作复杂表兜底 |

## 2. 图片向量化方案

### 方案 I1：VLM 生成图片描述，作为文本入库（当前最实用）

用视觉语言模型为每张图生成中文描述，**描述文本入向量库，原图路径存 metadata**。检索命中后可回显原图给用户。

```
入库文本：
【图 5-3】（来源：中国榴莲栽培技术, p.78）
图注：榴莲炭疽病叶片症状
VLM 描述：图中显示榴莲叶片正面出现多个近圆形褐色病斑，病斑边缘颜色较深
呈深褐色轮纹，中央灰白色并有轮纹状同心圈，部分病斑从叶尖向叶缘扩展并连片，
病斑外围有黄色晕圈。
上下文：（图片前后 200 字正文）

metadata: {"image_path": "...", "page": 78, "type": "image"}
```

| 项 | 说明 |
|---|---|
| 优点 | 与现有纯文本管道**零冲突**，不用换 embedding 模型、不用改向量库；描述可人工校对；可回显原图 |
| 缺点 | 一次性离线 VLM 成本（本项目 618 张图）；描述质量决定召回上限；细粒度视觉信息有损 |
| 适用 | 绝大多数场景，尤其是本项目这种"图是正文的插图说明"的农业技术文档 |
| 本项目现成资源 | `qwen_vl_max_client.py`（qwen-vl-max）已接好，只是没进 ingest 链路 |

**实现要点：**
1. **必须把图注（caption）和图片前后正文一起送给 VLM**，否则 VLM 只能给出泛泛的"一片绿叶"，而带上下文后能定位到"炭疽病病斑"。
2. Prompt 要求领域化输出（本项目：品种特征 / 病害症状 / 农事操作 / 器械设备），别让它写散文。
3. 过滤装饰性图片：Logo、页眉页脚、分隔线、尺寸过小（如 <100×100）的图直接跳过，否则污染向量库。
4. 描述 + 图注 + 上下文三者拼接入库，其中图注权重最高。

### 方案 I2：CLIP 类统一图文向量空间

用 CLIP / Chinese-CLIP / BGE-VL 等双塔模型，把图片和文本编码到**同一向量空间**，实现"以文搜图"和"以图搜图"。

| 项 | 说明 |
|---|---|
| 优点 | 支持图搜图（用户拍一张病叶找相似病例）；无需 LLM 生成成本；检索延迟低 |
| 缺点 | 需要**独立的图片向量库**（本项目 `image__vector_store.json` 就是这个空壳）；CLIP 只擅长"物体级"匹配，对"这是炭疽病还是叶斑病"这种细粒度专业判别很弱；中文需换 Chinese-CLIP |
| 适用 | 图搜图需求明确的场景；作为 I1 的补充而非替代 |
| 框架支持 | LlamaIndex `MultiModalVectorStoreIndex`；Milvus/Qdrant 多向量集合 |

### 方案 I3：ColPali / ColQwen 视觉页面检索（激进路线）

**完全绕过 OCR 和文本提取**。把 PDF 每一页直接当图片，用视觉 LLM 切 patch 编码，配合 late-interaction（MaxSim）多向量检索。

| 项 | 说明 |
|---|---|
| 优点 | 彻底免疫 OCR 错误、版式错乱、表格结构丢失；对图文混排、扫描件、复杂表格效果显著优于文本管道 |
| 缺点 | 每页产生上千个 patch 向量，**存储和计算成本高一到两个数量级**；必须搭配 VLM 做生成（不能用纯文本 LLM）；难以做精确原文引用/填空 |
| 适用 | 版式极复杂、OCR 已经失败的文档；有 GPU 预算 |
| 代表 | ColPali (PaliGemma)、ColQwen2、DSE (Document Screenshot Embedding) |

> 本项目有"精确原文填空"需求（`rag_llamaindex.py:178` `is_exact_answer_query`），依赖字面文本匹配，因此 ColPali **不适合作为主链路**，最多作为特定难解文档的旁路。

### 方案 I4：OCR 提取图内文字

对流程图、示意图、带文字标注的图表，用 OCR（PaddleOCR/MinerU 内置）抽出图内文字入库。

| 项 | 说明 |
|---|---|
| 优点 | 成本极低；对"图内含关键术语"的情况召回有效 |
| 缺点 | 只拿到零散词汇，丢失图的语义与空间关系；纯照片型图片无收益 |
| 适用 | 作为 I1 的补充特征，拼在描述后面 |

### 方案 I5：忽略图片，但保留占位与引用

不做向量化，仅在正文对应位置留 `[图 5-3：榴莲炭疽病叶片症状]` 占位符，metadata 挂图片路径。

| 项 | 说明 |
|---|---|
| 优点 | 零成本；保证正文语义连续；命中该段时可顺带回显图片 |
| 缺点 | 图片本身不可检索 |
| 适用 | **保底方案**。即使不做 I1，也应该做到这一步——而不是像现在这样把图片信息完全抹掉 |

### 图片方案对比

| 方案 | 实现成本 | 需换 embedding | 支持图搜图 | 专业细粒度 | 本项目建议 |
|---|---|---|---|---|---|
| I1 VLM 描述转文本 | ★★ 中 | 否 | 否 | 高 | **主方案** |
| I2 CLIP 统一空间 | ★★★ 中高 | 是（额外） | 是 | 低 | 后续可选 |
| I3 ColPali 视觉页 | ★★★★ 高 | 是（全换） | 是 | 中 | 不做主链路 |
| I4 OCR 图内文字 | ★ 低 | 否 | 否 | 低 | 作为 I1 补充 |
| I5 占位符引用 | ★ 极低 | 否 | 否 | — | **保底，立刻可做** |

## 3. 上游解析器选型（决定表格图片质量的真正瓶颈）

向量化方案再好，也救不了解析阶段就丢掉的信息。

| 工具 | 表格能力 | 图片能力 | 说明 |
|---|---|---|---|
| **MinerU** | 强，输出 HTML 表格 + caption | 强，切图 + `image` 类型 block | 本项目**已在用**，但输出被 `str()` 打平浪费了。注意：上一轮用的是**在线服务**，图片存 CDN 临时链接已失效；新流程须用**本地版**让图片落盘 |
| **Docling** (IBM) | 强，TableFormer 模型 | 支持图片分类与提取 | 输出 DoclingDocument，结构化程度高，与 LlamaIndex 集成好 |
| **Marker** | 中强，转 Markdown | 支持图片提取 | 快，输出直接是 Markdown |
| **Unstructured** | 中，`infer_table_structure=True` | 支持 | 生态成熟，`chunk_by_title` 好用 |
| PyMuPDF (`get_text`) | 无 | 无 | **本项目当前实际使用的**，纯文本流 |
| pypdf | 无 | 无 | 本项目 `auto_rag.py` 使用 |
| pdfplumber | 中（规则型，靠线框） | 弱 | 适合规整线框表 |

> 关键结论：**本项目不需要换解析器，MinerU 的输出已经够用**，缺的是一个把 MinerU JSON 按 `type` 分流的落地脚本。

## 4. 统一的目标数据结构

无论选哪个方案，建议 chunk 统一成下面这种形态（这也是修复本项目 `clean_chunks.jsonl` 的目标格式）：

```json
{
  "id": "sha1...",
  "doc": "中国榴莲栽培技术.pdf",
  "page": 45,
  "block_type": "text | table | image",

  "index_text": "用于向量化的文本（表格→Markdown/摘要，图片→VLM描述）",
  "display_text": "回显给用户看的内容",

  "metadata": {
    "caption": "表 3-2 不同榴莲品种果实品质比较",
    "section": "第三章 品种选择",
    "table_html": "<table>...</table>",
    "image_path": "images/xxx.jpg",
    "parent_id": "整表 node 的 id（行级切分时用）"
  }
}
```

要点：**`index_text` 和 `display_text` 分离**。向量化用翻译后的文本，展示用原始结构。本项目目前两者是同一个字段（`rag_llamaindex.py:929-935` 里 `text/index_text/display_text` 全赋同值），这是无法优化的根因之一。

## 5. 针对本项目的推荐路线

| 阶段 | 动作 | 涉及文件 | 预期收益 |
|---|---|---|---|
| **P0** | 重写 MinerU JSON 落地脚本：按 `type` 分流，`table_body`→Markdown 表，`image_body`→metadata + 占位符，正文→纯文本。**停止 `str()` 打平** | 新建 ingest 脚本 → 产出干净的 `clean_chunks.jsonl` | 消除 73% 污染、挽回被误丢的 22.8% 内容 |
| **P1** | 表格整表成 node，不参与 splitter；拼接 caption + 章节 | `rag_llamaindex.py:363` splitter 配置 | 695 个表格 chunk 从"裸数字"变为可检索 |
| **P2** | 618 张图片走 `qwen_vl_max_client.py` 离线生成描述入库（方案 I1） | 复用 `qwen_vl_max_client.py` | 图片从 0 召回变为可检索可回显 |
| **P3** | 数值型表格补 LLM 摘要 + 父子索引（方案 T2） | LlamaIndex `IndexNode` | 自然语言提问命中数值表 |
| **P4** | 决定 `image__vector_store.json` 空壳去向：接 Chinese-CLIP 做图搜图，或明确删除 | — | 消除架构歧义 |

**明确不建议做**：ColPali 全量替换（与本项目精确原文填空需求冲突）、Text-to-SQL（论文表格结构过于异构）、**换多语言 embedding**（实测对泰文这类低资源语言，跨语言对齐质量只有英文的零头，离线翻译成中文入库效果更好且成本更低 —— 详见 `docs/RAG_跨语言检索方案.md`）。

> **另一条独立发现的问题**：索引里 17% 是泰文 node（1287 个），而 embedding 是中文单语
> `bge-small-zh-v1.5`。实测泰文 chunk 的 UNK 率 43-62%，**存活 token 全是数字和标点**，
> 语义完全丢失，且会在数值类问题上被数字巧合命中 —— 与表格 HTML 碎片属同一类故障叠加。
> 处置方案见 `docs/RAG_跨语言检索方案.md`，落地对应实施流程的**阶段 4.5**。

## 6. 常见坑

1. **表格被 splitter 切断** —— 表头和数据分家，是最高频错误。表格必须整块。
2. **图片描述缺上下文** —— 不给 VLM 图注和周边正文，描述会退化成无用的泛泛之谈。
3. **装饰图污染** —— Logo、页眉、分隔线不过滤，向量库里塞满"一个绿色的圆形图标"。
4. **用正则事后擦解析器噪声** —— 这是本项目 `clean_text()` 的做法，属于治标。噪声应该在解析落地时就不产生。
5. **`index_text` 与 `display_text` 不分离** —— 导致"为了检索优化文本"和"为了展示保留原格式"两个目标互相打架。
6. **数值表直接向量化** —— `28.5 / 24.0 / 32.1` 这类纯数字的语义向量接近噪声，必须靠 caption 和摘要提供语义锚点。
7. **表格数值幻觉** —— 表头丢失后，LLM 会把数字和错误的列名配对。宁可不召回，不可召回残表。
