# 用户级权限隔离方案

> 目标：某一用户只能获取到某部分知识库的数据，同时只能调用某些工具。
> 日期：2026-09-03
> 关联文档：[Agent边界策略评估.md](Agent边界策略评估.md)（其中风险 #4「user_id 完全信任上游」正是本方案要解决的前提问题）

---

## 一、现状事实（决定方案空间的三个关键结论）

### 1. 身份链路是可伪造的，任何权限设计都必须先补这一层

| 事实 | 位置 |
|---|---|
| `get_current_user` 直接读 `X-User-Id` header，默认 `admin`，仅校验在 `APP_USERS` 集合内 | `durian__inference_api.py:603-607, 339-343` |
| 唯一鉴权是全局共享 API Key，与用户身份无关 | `durian__inference_api.py:561-576, 334` |
| 前端登录是纯浏览器校验（硬编码账号密码），后端无登录端点 | `frontend-vue/src/App.vue:26, 3068-3084` |
| API Key 打包进前端 bundle | `frontend-vue/src/App.vue:25` |

**结论**：知道 API Key 即可任意伪造 `X-User-Id`。在身份可信之前，做任何精细权限都是装饰性的。

### 2. 检索调用链没有任何过滤参数，chunk 也没有归属字段

- 检索路径固定：`_retrieve_node` → `adapter.retrieve(query, language)`（`durian_langgraph.py:1122-1161`）→ `retrieve_ragflow_grounded_context`（`durian__inference_api.py:9723`）。签名里没有 user、没有 filter。
- RAGFlow 请求体只有 `question / dataset_ids / page / top_k / similarity_threshold / ...`（`:2000-2016`）——**但 `dataset_ids` 本身就是天然的数据集过滤入口**。
- FAISS / LlamaIndex 路径是纯向量 top-k，无 filter（`:1864-1937`、`rag_llamaindex.py:934, 1134`）。
- chunk metadata 有 `doc / source_file / page / block_type / category / src_lang` 等（`rag_llamaindex.py:461-499`），**无任何用户/受众字段**。

**结论**：数据隔离要么走「检索后过滤」（不动索引），要么走「RAGFlow dataset 映射」（几乎零改造），要么「重建索引加受众标签 + 检索前过滤」（最彻底）。

### 3. 工具是硬编码 pipeline，不是 LLM 选工具

- LangGraph 固定边：`route → retrieve → compose → generate → trim_memory`（`durian_langgraph.py:545-556`），无 `bind_tools` / ToolNode。
- "工具"实际是四类能力：RAG 检索（固定节点）、Tavily web search（规则触发，`durian__inference_api.py:6758, 10146-10293`）、长期记忆读写（正则+规则触发，`durian_langgraph.py:432-449`）、图片病虫害分析（专用端点 `/classify_pest` 等，`:11421-11528`）。

**结论**：本项目「工具隔离」不需要 tool registry 过滤那套，等价于**功能开关/代码路径门控 + 端点级 RBAC**。

## 二、数据隔离：三个方案对比

先明确两个设计词：

- **scope（数据域）**：知识库的一个划分单位，如「基础种植知识 / 付费专栏 / 内部农艺资料」。
- **授权映射**：用户/角色 → 允许的 scope 集合，只能存在服务端。

### 方案 A：检索后过滤（post-retrieval filter）

```
retrieve(query) → top-k 候选 → 按 scope 标签过滤 → 送入 compose
```

- **做法**：给 chunk metadata 加 `audience`（scope 标签）；adapter 层按当前用户的 allowed scopes 过滤候选。
- **优点**：改动最小——不动索引结构，不动检索器，只改 `adapter.retrieve` 一处 + 建索引时打标。
- **缺点**：**召回质量随过滤比例劣化**。如果用户无权的数据占大头，top-k 里大量名额被无权候选占据，过滤后剩余证据可能不足，甚至被无权 chunk 顶掉有权 chunk（top-k 截断效应）。过滤必须发生在「送入上下文之前」，且不能把无权 chunk 的任何内容（含标题、分数）暴露给模型。
- **适用**：各 scope 数据量比较均衡、无权数据占比低、快速落地。

### 方案 B：检索前过滤（pre-retrieval / metadata filter）

```
retrieve(query, allowed_scopes) → 检索器只在自己的子空间内搜索
```

- **做法**：把 scope 条件下推到检索层，只在有权的子空间内做相似度搜索。
- **实现成本分层**：
  - RAGFlow（当前默认关，`DURIAN_RAGFLOW_ENABLED=False`）：**几乎零改造**——请求体已带 `dataset_ids`，按用户映射数据集即可（`:2000-2016`）。这是现成方案里最强、最干净的。
  - LlamaIndex：需要用支持 MetadataFilters 的检索路径。当前代码是裸 `index.as_retriever`（`rag_llamaindex.py:934`）+ 自研混合检索（`_hybrid_retrieve`, `:991`），BM25/RRF 分支**没有过滤语义**，需要自己把 filter 穿透到 dense 和 bm25 两条通路——工作量中等，且容易踩 dense/bm25 过滤不一致的坑（参考 RRF 去重的教训：两侧不同步会导致同一 node 表现异常）。
  - FAISS（当前默认后端）：原生无 filter。要么检索时带 ID 掩码（搜大 k 再筛，退化成方案 A），要么按 scope 拆成多个索引文件（即方案 C）。
- **优点**：无权数据根本不进候选池，召回质量不受无权数据占比影响；隔离语义干净。
- **缺点**：改造量大于 A；混合检索（dense+bm25）要双侧一致下推 filter。
- **适用**：中期目标方案。若 RAGFlow 启用，则 B 的成本最低、隔离最强。

### 方案 C：按 scope 分库（partition per scope）

```
每个 scope 一个独立 dataset / 独立索引目录；用户只挂载自己的集合
```

- **做法**：物理隔离。RAGFlow 按 scope 建多个 dataset；FAISS/LlamaIndex 按 scope 建多份索引（项目已有 `rag_llamaindex_storage/` 的先例，复制为 `storage_<scope>/` 即可）。
- **优点**：隔离强度最高——无权数据在物理上不存在于检索空间，不存在过滤逻辑写错导致泄露的风险；也便于按 scope 独立重建、评估、删除。
- **缺点**：跨 scope 检索（一个用户有权多个 scope）需要合并多路检索再 rerank；建库/运维成本随 scope 数量线性增长；同一文档跨 scope 共享要复制或引用。
- **适用**：scope 数量少（个位数）、隔离要求高（付费墙、内部资料）、或复用 RAGFlow dataset 机制时。

### 对比表

| 维度 | A 检索后过滤 | B 检索前过滤 | C 物理分库 |
|---|---|---|---|
| 改造成本 | 低 | 中（RAGFlow 路径低） | 中-高 |
| 隔离强度 | 中（依赖过滤代码正确性） | 强 | **最强** |
| 召回质量 | 随无权占比劣化 | 不受影响 | 不受影响 |
| 跨 scope 查询 | 天然支持 | 天然支持 | 需多路合并 |
| 运维复杂度 | 低 | 低-中 | 高（N 份索引） |
| 失败模式 | 过滤遗漏=泄露 | filter 下推不完整=混入 | 基本无泄露面 |

### 数据层结论

- **短期**（RAGFlow 未启用、FAISS 后端）：方案 A 起步——建索引时给 chunk 打 `audience` 标签（`rag_llamaindex.py:461-499` 的 `base_meta` 加一个字段），`adapter.retrieve` 按用户 scope 过滤。**过滤必须在 compose 之前完成，且过滤后候选不足时宁可 `source_missing`，不得放宽条件补数（fail-closed）。**
- **中期**：RAGFlow 启用时切方案 B/C——用户 → `dataset_ids` 映射，天然物理隔离。这是整套方案里性价比最高的一条路。
- 无论哪个方案，**上传入口必须先收紧**：`/rag/upload-pdf`、`/rag/rebuild`（`durian__inference_api.py:10710, 10718`）目前任何持 API Key 者可调用，上传直接进共享索引——这等于任何用户都能向全员知识库投料，是数据隔离的第一漏洞。

## 三、工具隔离：功能门控 + 端点 RBAC

因为工具是硬编码 pipeline，工具隔离落成两层：

### 1. 能力门控（agent 内部）

定义服务端的用户权限配置（角色 → 能力矩阵），例如：

```python
ROLE_CAPABILITIES = {
    "farmer":   {"rag": True, "web_search": True,  "memory": True,  "pest_analysis": True,  "rag_admin": False},
    "guest":    {"rag": True, "web_search": False, "memory": False, "pest_analysis": False, "rag_admin": False},
    "agronomist": {"rag": True, "web_search": True, "memory": True, "pest_analysis": True, "rag_admin": True},
}
```

执行点：

| 能力 | 门控位置 |
|---|---|
| web search | `adapter.retrieve` 内所有 `tavily_web_search` 调用前（`durian__inference_api.py:10146-10293`） |
| 记忆读写 | `MemoryStore.apply_user_message` / `get_user_memories` 入口（`durian_langgraph.py:432, 1710`） |
| 图片分析 | `/classify_pest`、`/analyze_pest*` 端点依赖注入层（`:11421-11528`） |
| 知识库管理 | `/rag/upload-pdf`、`/rag/rebuild` 仅 `rag_admin`（`:10710, 10718`） |

两点原则：

- **fail-closed**：用户不在任何角色里 → 全部能力为 False；能力查不到 → 拒绝，而不是放行。
- user_id 从可信身份层（见第四节）取得，**绝不从请求参数/header 直接取**。

### 2. 端点 RBAC（API 层）

现有 `verify_api_key`（全局 key）之上加一层 `require_role(...)` 依赖注入，管理类端点（上传、重建、记忆管理）与高成本端点（视觉模型分析）按角色收紧。前端登录改为调后端登录端点换 token，`localStorage['durian_current_user']` 不再作为身份依据。

### 与「未来若改造成 tool-calling agent」的关系

当前不需要 tool registry。但若日后迁移为 LLM 自主选工具的架构，门控位置自然变成「按角色过滤后的 tool 列表再 `bind_tools`」——权限矩阵设计（ROLE_CAPABILITIES）可以直接平移，不用推翻。

## 四、身份层：一切方案的前置条件

不解决这层，二、三节全部失效。最小可行改造：

1. **后端登录端点**：`POST /login`，账号密码（服务端存哈希，如 bcrypt），校验通过签发签名 session token（JWT 或等价物，含 `sub`、`role`、`exp`）。
2. **`get_current_user` 改为解析 token** 取 `sub`/`role`，彻底移除「默认 admin」（`durian__inference_api.py:603-607`）和 `X-User-Id` 的信任。
3. **角色只存在服务端**：token 里的 `role` 要么由服务端签发（对称签名下前端改不了），要么每次请求查服务端配置。绝不信前端传的任何身份字段。
4. 全局 API Key 降级为机器间凭证，或直接废除（登录后一律 token）。
5. `APP_USERS`、`LOGIN_ACCOUNTS`（`App.vue:26`）的硬编码账号体系迁到服务端。

顺带修复边界评估中的风险 #4（横向越权读写他人记忆）：身份可信后 `thread_id = f"{user}:{conv}"`（`:14346`）的隔离才真正成立。

## 五、推荐落地顺序

| 阶段 | 内容 | 效果 |
|---|---|---|
| 1. 身份层 | 后端登录 + token + 服务端角色 | 权限体系的地基；修掉风险 #4 |
| 2. 数据层短期 | chunk 打 `audience` 标签 + adapter 检索后过滤（fail-closed） | 数据隔离可用版 |
| 3. 工具层 | ROLE_CAPABILITIES 门控 + 端点 RBAC；先收紧上传/重建/视觉端点 | 工具隔离 + 堵投毒漏洞 |
| 4. 数据层长期 | RAGFlow 启用时切 `dataset_ids` 映射（方案 B/C） | 强隔离 + 不损召回 |

## 六、设计原则（写进代码评审清单）

1. **身份只来自服务端签发的凭证**，header 直传的 user 一律不可信。
2. **fail-closed**：scope/角色缺失、过滤组件异常时，结果是「查不到」而不是「都查到」。
3. **过滤在进入模型上下文之前**完成；无权 chunk 的任何内容（含标题、来源、分数）不得进入 prompt。
4. **授权映射只存服务端**；前端只做展示，不做任何鉴权判断。
5. 混合检索下推 filter 时 **dense 与 bm25 两侧必须同步**，否则检索结果会出现同 node 表现分裂（RRF 去重的既有教训）。
6. 每次检索/工具调用记录 user + scope + 工具名，可审计（谁在什么时候查了哪个域的数据）。
