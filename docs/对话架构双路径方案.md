# 对话架构双路径方案(强制 RAG 闭环 + ReAct Agent)

> 定案日期:2026-09-03。验证载体:`langgraph_dual_path_demo.py`(离线全流程已跑通),配套教学文件 `langgraph_tool_demo.py`(最小 agent 循环)、`langgraph_agent_full_demo.py`(workflow 骨架 + 循环)。
> 本文是设计文档,不含代码;所有"生产替换点"指明 demo 占位对应的真实实现位置。

---

## 一、背景与动机

现网聊天主链路(`/chat/stream3` → `durian_langgraph.py` LangGraph 运行时 → RAGFlow 检索)是**纯线性 workflow**:route → retrieve → compose → generate → trim_memory。该设计在三个场景下暴露不足:

1. **检索无重试**:一次检索质量差,没有第二次机会;`evidence_quality` 只用于生成侧免责,不反馈回检索。
2. **无工具能力**:模型不能调用天气、土壤、资产、任务系统等外部能力,复合问题(知识 + 实时数据)无法回答。
3. **规则词表在多语言下漂移**:追问正则只有 zh/en(durian_langgraph.py 的 `_GENERIC_FOLLOWUP_PATTERNS`),辱骂词表缺 ms/th(durian__inference_api.py `classify_casual_message`)。逐语言扩词表不可维护。

同时保留现网两个被验证的设计红线,不因新架构破坏:

- **实质问题必检索**(`rag_allowed` 机制):防止模型跳过检索产生幻觉。
- **逃生梯优先**:能从证据抽取/固定话术回答的,不进模型自由生成。

---

## 二、总体架构

```
请求(FastAPI 层验身份)
  → 预处理(实体识别、问题规范化)
  → 标签化(LLM,全语言统一映射到固定标签集)
  → 路由(查策略表,纯代码,语言无关)
      ├─ 路径 A:强制 RAG 闭环(高风险问题)
      │    检索 → 重排 → 证据充分性判断 ─┬─ 充分 → 带引用生成
      │                                  ├─ 不充分且未超限 → 改写问题 → 重查(循环≤2次)
      │                                  └─ 超限仍不充分 → 诚实拒答(禁止退化自由生成)
      └─ 路径 B:ReAct Agent(普通问题)
           agent ⇄ tools 循环(模型自主决定调哪些工具)
           → 综合生成
  → trim_memory(上下文裁剪,两路共用)
  → checkpoint 落盘(SqliteSaver,thread_id 记忆)
```

核心分工原则:**流程骨架由图确定,类型判断由模型完成,路由决策由策略表完成,工具执行由编排层完成**。任何一层都不越权。

---

## 三、路径 A:强制 RAG 闭环

### 3.1 预处理

- 识别关键信息:作物、病害/虫害、地区、时间、生育期、农药、施肥量、品种编号等;必要时把口语化问题规范化为利于检索的形式。
- 语言无关的结构信号在此一并提取:品种编号(如 Dxxx 模式,全语言通用)、图片上下文标志。
- 产出随 state 传递,后续标签化与检索共用。

### 3.2 标签化(语言相关的一半,交给 LLM)

- **一次 LLM 结构化输出**,把任意语言的问题映射到固定标签集。与主项目已有的 `route_context_with_llm`(durian__inference_api.py:4307,语义路由本就是 LLM)合并为同一次调用,零新增延迟。
- 标签集(全语言共用一套,新增语言零成本):
  - **intent(主标签 + 可空 secondary 数组,支持复合问题)**:disease_diagnosis 病害诊断 / pest_diagnosis 虫害诊断 / disease_control 病害防治 / pest_control 虫害防治 / fertilization 施肥管理 / irrigation 灌溉管理 / nutrient_diagnosis 营养缺素诊断 / flowering_management 花期管理 / fruit_management 坐果疏果 / pruning 修剪 / soil_management 土壤 / weather_risk 天气风险 / harvest 成熟采收 / variety_query 品种 / orchard_operation 园区日常 / yield_query 产量 / pesticide_query 农药 / regulation_query 标准法规 / general_knowledge 普通知识 / **unknown 兜底**
  - **growth_stage(可空)**:seedling / vegetative / pre_flowering / flowering / fruit_set / fruit_development / pre_harvest / harvest / post_harvest
- 治理约定:
  - 必须保留 unknown 兜底,不给模型硬塞出口;
  - 标签集带版本号,演进需评审;线上持续统计标签分布,分布突变即报警;
  - 多意图问题必须用 secondary 数组表达,禁止"硬选一个"。

### 3.3 路由(语言无关的一半,纯查表)

- **策略表**(数据,非代码逻辑):`{disease_control, pest_control, pesticide_query, fertilization, nutrient_diagnosis, regulation_query}` → 强制 RAG;其余 → 路径 B。策略表可评审、可 diff、可回滚。
- **语言无关安全兜底**:剂量/浓度的数字模式(数字+单位)命中即强制 RAG。理由是错分代价不对称——该强制而漏检的代价是幻觉,该 agent 而误判成强制的代价只是多一次检索,所以兜底永远偏向检索侧。
- 高置信短路仍保留在规则层:品种编号类精确题(exact)、纯闲聊(casual),零成本零错误,不消耗 LLM 判断。

### 3.4 检索

- 复用现网唯一事实检索路径:`retrieve_ragflow_grounded_context`(durian__inference_api.py:9723)→ RAGFlow `/retrieval` 混合检索(:2001),含域约束、缓存、精确题参数分档。
- 检索查询使用 route 产出的 `rag_query`(改写后的规范化查询),不是用户原话。

### 3.5 重排与筛选

- 不把向量库 TopK 原样交给模型:用 rerank(BAAI/bge-reranker-v2-m3 已在项目配置中)重排,过滤低相关条目。
- 过滤阈值按 intent 分档可调(如 exact 类收得更紧)。

### 3.6 证据充分性判断(grade)

- 判断"资料能否支撑回答",而非"搜到了东西"。demo 中曾出现纯关键词分数达标但答非所问的误判(虫害条目被判可回答卷叶问题),教训固化为规则:**分数达标 + 问题核心症状词/关键实体必须被证据覆盖**。
- 生产实现为 LLM 结构化输出(sufficient: yes/no + 理由),评审项按 intent 定制:
  - pesticide_query:证据中必须出现剂量/浓度数字;
  - disease_control / disease_diagnosis:必须覆盖症状词;
  - regulation_query:必须命中具体标准名称/条款号。
- 标签在这里第一次反哺下游质量。

### 3.7 带引用生成

- 强约束提示词:只准依据证据作答,答案须附来源(文档名/标准名/条目 ID)。
- 逃生梯语义保留在路径 A 内部:exact 类继续走确定性抽取(durian_langgraph.py 的 `extract_exact_answer` 机制),不从模型记忆作答。

### 3.8 改写重查循环

- 不充分 → 根据查询与已检结果改写问题 → 重查 → 再判断。上限 **2 次**。
- 改写由 LLM 完成(示例:"番茄叶片卷曲怎么防治" → "温室番茄高温生理性卷叶 成因 应对"),state 内计数器控制上限,防止无限循环。
- 每次重查沿用同一套重排 + grade,保证口径一致。

### 3.9 诚实拒答

- 超限仍无充分证据:拒答 + 请求补充(品种/环境/症状细节),**禁止退化为模型自由回答**——这是路径 A 的红线,对齐现网"实质问题必检索"精神。
- 拒答模板四语化(zh/en/ms/th),沿用 `_clarification_reply` 的四语 dict 模式。

## 四、路径 B:ReAct Agent

### 4.1 适用范围

路由判定为非强制的所有问题,包括:实时数据类(天气/墒情)、复合问题(知识 + 实时)、`general_knowledge`、以及标签为 unknown 的问题。

### 4.2 循环结构

- 单 agent 节点内嵌 agent ⇄ tools 循环(教学文件 `langgraph_tool_demo.py` 为最小形态):模型点单(tool_calls)→ 编排层执行 → ToolMessage 按 tool_call_id 回填 → 模型二轮消化,直至不再点单。
- 工具清单常驻注入每次模型调用(compose 产出的只是对话内容,工具清单在 generate 调用时写入请求体,不进消息历史)。
- **循环保险丝**:state 内轮次计数 + 全局 recursion_limit,超限降级为无工具生成并明示"未能获取实时数据"。
- 并行 tool_calls 协议层天然支持,复合问题(天气 + 品种)一轮多点。

### 4.3 工具规划

- **首期工具**(5-10 个以内,单 agent 扛住,不拆多 agent):
  - `search_kb`:农业知识库检索——**复用路径 A 的同一检索函数**,RAG 在这里只是一个工具;
  - 天气接口、土壤墒情、农药数据库、农业标准库(后期接 MCP)。
- **MCP 接入形态**:启动时 MCP client 连 server、list_tools 自动转工具 schema;运行时 tools 节点把调用转发给对应 server。模型与编排层不感知工具在本地还是远端。
- **规模阈值**(何时才拆 supervisor + 领域 agent):工具 schema 总量 > 15k token 或工具 > 20 个、权限体系要求隔离、相似工具频繁选错。当前不满足,由测量数据触发,不提前分层。
- 三处与 agent 数量无关的硬规则:执行层强制带用户身份;创建/修改/删除类工具加确认与审计;MCP 超时与异常格式兜底(异常回填给模型,不让图崩溃)。

### 4.4 链式调用示例(已验证)

"根据明天北京的天气,判断冬小麦需不需要灌溉" → query_weather → query_soil → search_kb(灌溉标准)→ 综合判断"无需灌溉",引用标准来源。体现步骤间的真实依赖:前一步结果决定下一步查询。

## 五、多语言方案

三层结构,只有第二层需要每语言配置:

1. **结构信号(全语言共用)**:编号正则、长度、图片标志、tool_call。
2. **封闭集词表(每语言一份,小而稳)**:致谢、追问、拒答/澄清模板。按 `_clarification_reply` 的四语 dict 模式维护。**待补缺口**:追问正则补 ms/th(如 "lagi""อีก" 类)、辱骂表补 ms/th。
3. **开放词汇判断(一次 LLM 调用,全语言)**:即 3.2 的标签化。严禁逐语言扩展关键词表。

泰文特殊注意:无空格分词导致传统词频相似度失效(项目已有踩坑记录),但标签化方案对泰文天然免疫(LLM 直接理解);嵌入锚点方案(备选)亦不受影响,因多语言嵌入模型原生支持。

**growth_stage 的下游红利**:语料分片阶段打生育期标签后,检索可按 growth_stage 做元数据过滤("花期管理"只在花期片检索),是检索精度的免费提升。依赖:重新分片流程(RAG 重新分片实施记录)增加打标步骤。

## 六、状态与记忆

- **State 字段规划**:messages(reducer:追加/更新/删除)、user_query、labels、route、rag_query、evidence、sufficient、retry_count、answer,及主项目已有的 working_memory / topic_memories / rolling_summary / long_term_memories。
- **Checkpoint**:SqliteSaver + thread_id,每个 superstep 落盘;多轮记忆闭环不变。
- **trim_memory**:超上限用 RemoveMessage 删最旧(主项目 `_trim_memory_node` 机制,上限 12 条)。
- **长期记忆**:用户显式陈述抽取与拒收规则(问句不存、敏感词拒收)原样保留。

## 七、评估方案

- **双口径分离**:强制 RAG 路径与 Agent 路径分别统计,各自有确定的行为边界。
  - 路径 A:沿用 known-item 体系(Hit@K、可达率),外加"拒答正确率"(该拒的是否拒了、不该拒的是否答了);
  - 路径 B:新增工具选对率、工具链完成率、最终答案事实核对抽样。
- **标签级指标**:intent 分类准确率(可人工标注抽样集)、各标签的检索成功率——评估口径从"问法"升到"问题类型"。
- **循环启用决策**:先统计线上 `evidence_quality` 为 none/low 的轮次占比(现有日志可算):<5% 不启用循环;<15% 且集中于某类问法,针对性启用;同时分析是否为知识库缺料(缺料时重查无用,应补语料)。

## 九、实施阶段

1. **阶段一(已完成)**:demo 验证行为模式——`langgraph_dual_path_demo.py` 双路径全流程、改写重查循环、多工具链式调用、标签制路由。
2. **阶段二**:graduation 进 `durian_langgraph.py`——generate 节点改造为"逃生梯 + 条件性 ReAct",retrieve/compose 降级为 generate 内部步骤或保留为节点(待实施时按延迟实测定);route 节点瘦身(短路 + 消歧),标签化并轨 `route_context_with_llm`。
3. **阶段三**:MCP 接入(先任务系统单域验证 schema 质量、description 对选对率的影响、超时兜底),再接资产系统。
4. **阶段四**:语料分片打 growth_stage 标签,启用检索元数据过滤。

## 十、风险与开放问题

- **标签错分导致绕过强制 RAG**:靠 unknown 兜底 + 剂量数字语言无关兜底 + "不确定偏向检索侧"策略压低;错分率进入阶段二后的常规监控。
- **标签集治理**:unknown 占比过高说明标签集设计有缺口,需定期评审迭代。
- **延迟预算**:路径 B 每次工具循环多一跳 LLM;路径 A 规则命中时零新增。上线前按 P50/P95 实测。
- **现网双 RAG 并存**:本地 llamaindex 只服务 legacy `/chat/stream2`,本架构所有检索均指向 RAGFlow 数据集;本地语料优化成果需同步进 RAGFlow 才在线上生效(见 RAG 双管线现状)。
