# 图片 VLM 描述 + 扫描件 OCR：技术选型与实施设计

> 决策文档。状态：**选型已定，待用户批准试点**。
> 关联：`docs/RAG_表格图片向量化方案.md`（早期 T1-T5/I1-I5 方案论证，本文是其 I1 与 OCR 部分的落地选型）。
> 背景数据：当前语料 **0 个图片 node**（图片完全不进索引）；`TH_ACFS_TAS_Durian_TH_81.pdf`（泰国国家标准，37 页扫描件）**整体不可见**。

## 一、要解决的两个问题

| # | 问题 | 现状 | 影响 |
|---|---|---|---|
| ① | **语料里的图片内容不可检索**（I1 方案） | 图片 node 数 **0**；仅 12 个 node 因图注恰好出现在正文文本流而带进 caption | 用户问"叶片发黄长什么样""修剪示意图"，检索只能靠图注文字；2024 版图版（`Gambar rajah`/`Jadual`）贯穿全文，换版后缺口更大 |
| ② | **37 页泰国国家标准扫描件整体不可见** | 扫描件检测（文本层稀疏）→ 管道直接排除 | 官方分级/收购标准对检索完全不存在；这是收录目录里权威性最高的一类文档 |

**质量基线（MinerU 教训，本文所有验证设计的由来）**：MinerU 的 OCR 环节曾跨文档注入中文幻觉（`率达到` 哨兵，58 个片段）、且把 `tanah`(土) 错成 `tidak`(不)——**反义改词是合法词、读着通顺、正则扫不出、无对照时不可枚举**。任何 OCR/VLM 方案的验收必须按"错误会不会读起来像对的"来设计，不是按"有没有乱码"。

## 二、选型结论（先给答案）

| 任务 | 主选 | 理由一句话 |
|---|---|---|
| ①图片描述 | **Qwen2.5-VL-7B-Instruct（Q4 量化，MLX/llama.cpp 本地跑）** | 单模型同时覆盖"看懂农业图版 + 读图内多语言文字"两项需求；Apache 2.0；M 系列芯片 4bit 可用速（详见 2.1） |
| ②扫描件转写 | **同一模型 + Typhoon OCR（泰文专精）双引擎交叉** | 泰文 OCR 是出了名的难例（无词间空格+叠写声调），单一引擎的静默错误率不可接受；两个独立引擎互为对照（详见 2.2） |

**核心决策：一个 VLM 承担两个任务**，而不是"图片用 VLM、扫描件用传统 OCR"两个栈。

## 三、候选与淘汰理由

### 3.1 任务①：图片描述（VLM 选型）

| 候选 | 参数量 | 许可 | 优势 | 淘汰/降级理由 |
|---|---|---|---|---|
| **Qwen2.5-VL-7B** ✅ | 7B | Apache 2.0 | OCR 能力一线（密集文字+多语言标签）、图表理解强、有 grounding（能报图中位置）、MLX/llama.cpp 在 Apple Silicon 成熟 | —（主选） |
| Qwen2.5-VL-3B ✅ | 3B | Apache 2.0 | 速度快一倍、内存减半 | 降为**试点验证失败的降级选项**：先上 7B，速度不可接受再降 |
| MiniCPM-V-2.6 | 8B | Apache 2.0（部分组件另有条款） | OCR 与密集文字强 | 与 Qwen2.5-VL 能力重叠，作为**第二引擎**留用（交叉验证用），不做主力——避免两套提示词工程 |
| Florence-2 | 0.7B | MIT | 极快极小 | 输出是短 caption/检测框，**语义深度不够**——农业图版的"施肥 schedule/修剪步骤"这类关系性内容描述不出来 |
| SmolVLM2 | 0.5-2.7B | Apache | 极小 | 同上，语义深度不足 |
| PaliGemma2 | 3B-10B | **Gemma 许可**（有使用限制条款） | Google 出品 | 许可条款对商用分发有限制，项目数据未来可能公开，排除 |
| 云 API（GPT-4o / Gemini） | — | 商业 | 质量顶尖 | **违反本项目约束**：语料为本地私有数据、远端服务已明确禁用（127.0.0.1 隧道教训同源——依赖外部服务等于把数据送出边界），且 623 张图的 API 成本不可控 |

### 3.2 任务②：扫描件转写（泰文 OCR 选型）

泰文 OCR 是公认难例：**词间无空格**（识别后还需要分词后处理）、叠写声调、字符堆叠。引擎选型：

| 候选 | 泰文支持 | 评估 |
|---|---|---|
| **Typhoon OCR**（SCB 10X，泰国团队）✅ | **泰文专精**——专为泰文文档设计 | 首选引擎之一：本项目的泰文语料教训（两套损坏方案、反义改词）恰恰说明泰文 OCR 的错误形态是"读起来通顺的错词"，专精引擎的先验概率最低 |
| **Qwen2.5-VL-7B** ✅（与任务①同模型） | 多语言 OCR 覆盖泰文 | 第二引擎：与 Typhoon **互相独立**地转写，diff 出分歧点交人工裁决 |
| Tesseract + `tha` 语言包 | 有 | **降级为第三意见**：`tha` 训练数据老、对叠写声调错误率高，单独扛不起，但作为免费的第三方投票仍有价值 |
| PaddleOCR | 新版支持泰文 | 保留观察：中英一线强，泰文属多语言长尾；如果双引擎 diff 率低（<2%），不需要它 |
| EasyOCR | 支持泰文 | 淘汰：CRNN 老架构，在叠写声调上的已知错误率高于上述所有 |
| 云 OCR（Google Vision 等） | 优 | 同 3.1 淘汰理由 |

**为什么必须双引擎**：MinerU 事故的本质是"单引擎的系统性错误没有对照"。`tanah→tidak` 这种错误，任何**单**引擎都可能以自己的方式犯；两个架构独立的引擎（一个泰文专精、一个通用多语言）在同一处给出**不同**输出时，那个位置就是可疑点，交人工裁决。分歧行数本身就是质量指标——如果 37 页里 diff 率超过 5%，说明文档质量差到需要换方案，这个信号比任何抽样都早。

### 3.3 为什么不用 ColQwen2 视觉直检（ColPali 路线，方案 I3）

搜到的实践（页面截图直接做 multi-vector 检索、跳过 OCR/描述）技术上成立，但**暂不选**：

1. 引入第二个向量存储（视觉向量与文本向量两套索引、两套召回融合），现有 RRF 架构要大改
2. 检索命中后仍需 LLM 看图回答——**绕不开 VLM**，等于模型照买、架构还更复杂
3. 现有 BM25 通路对图片节点完全失效（截图里没有文本）——丢失词法兜底

它的正确启用时机：将来若发现"图版里的空间/视觉关系信息靠文字描述丢失严重"（比如病虫害症状图的病灶位置），再作为增量层加。**先用文字路线把图片内容从 0 做到可检索，架构简单且与既有体系同构。**

## 四、管道集成设计（与既有体系同构）

### 4.1 图片 → node

```
raw/pdfs/*.pdf
  └─ parse_pdfs() 增加: page.get_images() 逐图导出 PNG（记录页码+bbox）
       └─ VLM 批量描述（见五、执行流程）
            └─ 入 chunks.jsonl:
               block_type = "image"（复用既有整块绕过 splitter 的分支）
               index_text  = "【图片】" + 中文描述 + 原文关键词（图内标签词）
               display_text = 中文描述
               metadata    = { image_path(本地PNG), caption(正文流中可关联到的
                               图注), page, src_lang }
```

要点：
- `block_type="image"` 已在 `load_rechunk_nodes()` 的整块分支里——**管道零改动**，只是历史上从未有过 image 行
- 图注关联：正文流中 `Gambar rajah N` / `รูปที่ N` / `Figure N` 模式与图序对齐（PyMuPDF 提取文本时保留），关联上的图注**追加进 index_text**——图注是人工写的检索锚点，价值高于 VLM 描述
- 描述语言策略：**中文描述主体 + 保留图内原文标签词**（如品种编号 `D24`、`Gambar rajah 40`、泰文术语原词）。中文描述服务于中文 dense 查询，原文关键词保留给 BM25 和对应语种查询——与泰文双语拼接的"多语言共一 node、各语言各走各的通路"哲学一致

### 4.2 扫描件 → 走既有管道

```
TH_ACFS_TAS_Durian_TH_81.pdf（37 页扫描件）
  └─ 每页高 DPI 渲染成 PNG
       └─ 双引擎转写（Typhoon OCR + Qwen2.5-VL）→ 分歧点人工裁决 → 合并文本
            └─ 产出"文本页"，走 rag_rechunk.py 正常管道
               （表格/图版识别与正文同规则；normalize_thai() 自动生效）
```

要点：
- **不加新 block_type、不改 rag_llamaindex.py**——OCR 产物就是普通 text chunk，现有全部泰文优化（规范化、3-4gram、双语拼接若翻译）自动适用
- 转写文本的泰文若含损坏形态，`normalize_thai()` 在运行时兜底（幂等已验证）

## 五、质量验证协议（MinerU 教训制度化）

| # | 验证 | 方法 | 通过线 |
|---|---|---|---|
| V1 | **双引擎 diff 率** | Typhoon 与 Qwen 转写逐页对比（Thai 分词后按词比对，用 pythainlp） | diff 率 <5% 可批量；5-15% 抽人工裁决分歧行；>15% 停下换方案 |
| V2 | **泰文词典检查** | 转写词经 pythainlp 分词后，查"不在词典且非数字/专名模式"的词——MinerU 的 602 个 OCR 垃圾实词就是这么抓的（`agenagen`/`atopu` 类粘连错拼） | 垃圾词占比 <2% |
| V3 | **反义/近形词高危名单** | 泰文近形词清单（`tanah/tidak/tahun` 这类）全文扫描人工过——正则扫不出的错，名单能兜一部分 | 高危词零命中错例 |
| V4 | **人工抽检** | 每批随机抽 5% 逐句对照原图 | 错误率 >3% 停批 |
| V5 | **图片描述忠实性** | 试点期 10-20 张图人工对照（描述说了图里没有的内容 = 幻觉，比漏说严重） | 幻觉 0 容忍，漏要素 <30% 可接受 |
| V6 | **哨兵复用** | `率达到` 等既有哨兵 + 新增扫描件哨兵集 | 零命中 |

**V5 的幻觉零容忍与 V4 的错误率容忍不对称，是有意的**：图片描述错一句会主动误导检索与回答（错误答案），漏一个要素只是少一条召回路径（缺答案）。

## 六、成本估算与执行顺序

| 阶段 | 内容 | 耗时（M 系列芯片，Q4 量化 7B） |
|---|---|---|
| P0 试点 | 模型下载（~6GB）+ 10-20 张图描述 + 3-5 页扫描件双引擎转写 + **全套 V1-V6 协议首跑** | 半天（含人工评审） |
| P1 扫描件 | 37 页 × 双引擎转写 + 裁决 | 转写 ~1-2h + 人工裁决 1-2h |
| P2 图片批次 | 2024 版图片（优先，新内容）→ 旧语料 623 张（按文档价值排序） | 7B 约 10-15s/图，全部 ≈ 2-3.5h 机器时间 |
| P3 入库 | 图片 node 入 chunks.jsonl + OCR 文本走管道 → 重建索引 → known-item/金标回归 | 重建 ~2min + 评估 ~5min |

**顺序理由**：扫描件先于图片批次——37 页解锁一整份官方标准文档（权威性最高），且双引擎协议需要先在小批量上标定 diff 率基线；图片批次是量大但单件简单的活，放后。

## 七、风险表

| 风险 | 应对 |
|---|---|
| 7B 在 MPS 上速度不可接受（>30s/图） | 降级 Qwen2.5-VL-3B（质量差多少在 P0 试点对比 10 张图就知道） |
| Typhoon OCR 权重/许可变更（相对较新的模型） | P0 试点即验证可用性；备用双引擎组合 Qwen + Tesseract（V1 阈值收紧到 8%） |
| 2024 版图版是矢量图而非位图 | PyMuPDF 按区域渲染成 PNG 再送 VLM，矢量/位图无差别；风险实际不存在，列入以防"get_images 抓不到矢量元素"的误解 |
| VLM 对马来文/泰文图内标签 OCR 错误 | 图内标签错误进 index_text 会污染检索——V5 幻觉检查 + 原文关键词**只保留高置信短词**（品种编号/量纲），长句一律以中文描述为准 |
| 扫描件里也有表格/图版 | OCR 文本对表格的还原能力有限；若 37 页里表格占比高（目录显示有分级表），表格页改用 VLM 表格转 Markdown 而非行式 OCR——P0 试点时数一下表格页占比再定 |
| 显存/内存不足 | Q4 量化 7B 约 5-6GB，M 系列 16GB+ 内存无压力；若仍不足降 3B |
