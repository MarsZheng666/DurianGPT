# 会话隔离机制：现状梳理

> 梳理日期：2026-09-06
> 本文描述的是**已实施的现状**，与 `用户级权限隔离方案.md`（设计方案，大部分未实施）互补。
> 关键代码：`platforms/durian__inference_api.py`、`platforms/durian_langgraph.py`

## 一、总体思路

会话隔离不是靠单一模块实现的，而是三层机制叠加，每层依赖上一层给出的"当前用户是谁"：

```
身份识别（X-User-Id） → 对话记录归属（owner 过滤） → LangGraph 运行状态隔离（复合 thread_id）
```

- **会话/记忆层面**：隔离是真实的（owner 过滤 + 复合 thread_id + checkpointer 分线程），越权路径基本堵死。
- **身份层面**：建立在可伪造的明文 header 上，体系安全性上限卡在这里。
- **知识库数据层面**：完全无隔离，RAG 索引全局共享。

## 二、第一层：身份识别

每个请求带两个 header：

| Header | 作用 | 性质 |
|---|---|---|
| `X-API-Key` | 全项目共享的一把钥匙，只挡无关外部流量，不区分用户 | 单一共享 |
| `X-User-Id` | 身份来源，到用户白名单里校验 | 可伪造的明文 |

- 白名单由环境变量 `DURIAN_APP_USERS` 配置，默认 `admin,admin2`；请求不带该 header 时默认按 `admin` 处理（`durian__inference_api.py:541-545`、`:281-285`）。
- 前端把用户名和共享 API key 存 localStorage，每次请求携带；本地会话列表按用户名分开存储（`frontend-vue/src/App.vue:64-77`）。

**弱点**：用户名是明文 header，谁都可以填。后面隔离做得再严密，身份本身可伪造——这也是 `用户级权限隔离方案.md` 把"身份层是前提"列为第一结论的原因。

## 三、第二层：对话台账（owner 过滤）

后端有一个基于 SQLite 的对话存储（`ConversationStore`，`durian__inference_api.py:7705`），核心设计：

- `conversations` 表带 **owner 列**（带索引），`messages` 表通过外键挂在会话下。
- 所有 CRUD（列出 / 读取 / 删除 / 追加）**强制带 owner 查询条件**——不是"查出来再看归属"，而是查询本身就限定在当前用户的范围内。
- 所有 `/conversations*` REST 端点都注入身份识别依赖，先拿到用户名才查库。

因此既读不到、也删不掉别人的会话；前端列表与后端过滤结果一致。

**历史背景**：建表代码里有专门的迁移逻辑（ALTER 添加 owner 列，旧数据默认归 admin，`durian__inference_api.py:622-628`）——项目最初是单用户的，多账号隔离是中途改造的。

## 四、第三层：LangGraph 运行状态隔离

LangGraph 的 checkpoint 机制 + 复合 thread_id，是整个机制的核心：

1. **thread_id = `用户名:会话ID`**（`durian__inference_api.py:10665`）——把身份直接编进线程标识，不同用户即使会话 ID 相同也是完全不同的线程，各自的中间状态、消息历史、Agent 推理过程完全分开。
2. **前置归属校验**（`durian__inference_api.py:10647-10649`）：进入流式问答前，先用当前身份去对话台账查这条会话。由于台账查询本身带 owner 过滤，会话不属于你则查不到、直接 404，根本走不到构造 thread_id 那一步。
3. 由此保证：**thread_id 里的用户名永远来自服务端验证过的归属关系，而不是客户端说了算**。这两层配合堵住了"猜 thread_id 越权"的路。
4. checkpoint 由 SqliteSaver 持久化（`durian_langgraph.py:500-523`），graph compile 时挂载。

**注意**：checkpoint 存储本身不懂权限、没有归属字段，它的隔离完全靠入口处的台账校验间接担保。如果入口校验被绕过，这一层没有自我防御能力——单点全在台账那道关上。

## 五、附加层：跨会话长期记忆

- 存 `user_memories` 表，`UNIQUE(user_id, normalized)` 防重复（`durian_langgraph.py:315-324`）。
- user_id 从复合 thread_id 前缀解析（`durian_langgraph.py:526-527`），即经过归属校验的用户名，天然按用户分开。

## 六、三份存储的关系

项目有三份**独立的 SQLite 持久化存储**，都在磁盘上、都跨重启存活，没有只存在内存里的：

| 存储 | 文件 | 职责 | 结构化程度 |
|---|---|---|---|
| 对话台账 | `durian__conversations.db` | 回答"你是谁、这场对话归不归你"（**准入，权限事实来源**） | 完全结构化：关系表 + 外键 + owner 索引 |
| 短期记忆（checkpoint） | `durian_langgraph_checkpoints.sqlite` | 回答"这场对话进行到哪了"（会话内状态） | 半结构化：外壳是关系表，内容是序列化大对象 |
| 长期记忆 | `durian_user_memories.sqlite` | 回答"系统对这个人累积了解了什么"（跨会话画像） | 结构化关系表 |

三者的依赖关系：**checkpoint 和长期记忆信任 thread_id / user_id，而 thread_id 的合法性由台账在入口处担保**。只有台账带 owner 字段，这是前置校验必须查台账的根本原因。

### 关于 SQLite 本身

三个库都是 SQLite——嵌入式、无服务进程、单文件、随项目走、零运维。区别在用法：

- **台账、长期记忆**："表结构即语义"，owner 过滤是真正的 SQL 级查询条件，走索引。
- **Checkpoint 库**："拿关系型数据库当 KV 存储"——表结构由 SqliteSaver 定死，每条 checkpoint 是序列化后整块存取的大字段，不应也不需要用 SQL 去碰它内部。

## 七、未做到的部分

会话隔离 ≠ 知识库数据隔离。以下内容在 `用户级权限隔离方案.md` 中有设计、但**代码零实施**：

- `ROLE_CAPABILITIES` RBAC 能力矩阵（工具/功能门控）
- chunk 打 `audience` 标签做检索后过滤（方案 A）
- RAGFlow `dataset_ids` 按用户映射（方案 B/C）
- `/rag/upload-pdf`、`/rag/rebuild` 仅靠共享 API key，任何知道 key 的人都能向共享索引投料

**一句话总结**：会话隔离的骨架是完整自洽的——归属校验过的用户名 → 复合 thread_id → checkpointer 分线程存状态 → 对话表按 owner 读写，四者环环相扣；但体系立在"明文 header 声明身份"的可伪造地基上，且只覆盖会话层、不覆盖知识库数据层。前者是设计取舍，后者是待办事项。
