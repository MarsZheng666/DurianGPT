# RAG 跨语言检索方案 —— 为什么选离线翻译而非多语言 embedding

> 结论：本项目的非中文语料（泰文 / 英文）应在**入库阶段离线翻译成中文**，而不是把
> embedding 换成 `bge-m3` 之类的多语言模型。
> 依据：本地实测，非推断。
> 制定日期：2026-09-02

---

## 一、问题从哪来

索引 7668 个 node 里，语种构成是混合的：

| 分组 | node 数 | 占比 | 语种 |
|---|---|---|---|
| FAQ | 2476 | 32% | 中文 |
| 文献（MinerU） | 3262 | 43% | 主要英文 |
| 泰文 DOCX | 1287 | **17%** | 泰文（来自 3 份手册的 651 个 chunk 切分而成） |
| SOP/LKE PDF | 643 | 8% | 中文 |

而 embedding 模型是 **`bge-small-zh-v1.5`，中文单语模型**。这是一个架构性错配。

发现路径：建评估体系时量化到 —— 可达金标 139 条中 126 条（91%）是"中文提问 + 非中文原文"，其中 **125 条（99%）被判检索失败**。排查后确认失败主要是评估口径问题（见 `docs/RAG_评估体系.md`），但顺带暴露了底层的语种错配。

## 二、实测一：中文单语模型对非中文语料做了什么

### 分词层面

```
词表大小:  bge-small-zh = 21,128    XLM-R (bge-m3) = 250,002
```

| 语言 | bge-small-zh (中文单语) | XLM-R (多语言) |
|---|---|---|
| 中文 | 11 token，UNK **0%** | 11 token，UNK 0% |
| 英文 | 12 token，UNK 8%（subword 勉强可用） | 10 token，UNK 0% |
| **泰文** | 1 token，UNK **100%** | 6 token，UNK **0%** |
| 马来文 | 12 token，UNK 8% | 8 token，UNK 0% |

纯泰文句子 `จุดเด่นของทุเรียนชุมพร` 在中文模型里被压成单个 `[UNK]`；在 XLM-R 里切成
`['▁จุด','เด่น','ของ','ทุ','เรียน','ชุมพร']` —— 有意义的子词序列。

### 向量层面：一个被修正的假设

我最初推断"泰文 node 已在向量空间塌缩成一个点"。**实测否定了这个推断**：

```
中文对照组 4 条互不相同文本，两两余弦相似度均值  0.6000
泰文       4 条互不相同文本，两两余弦相似度均值  0.7662
```

0.77 高于中文的 0.60（区分度下降），但远不是塌缩（≈1.0）。

**查清原因后发现，真相比"塌缩"更值得警惕。** 真实泰文 chunk 的 UNK 率是 43-62%，
存活下来的 token 是这些：

```
node 2 存活 token: ['5', '(', '1', ')', '50']                        ← 仅 5 个
node 3 存活 token: ['50','5','.','5','-','6','.','5','1',',','600',...] ← 全是数字与标点
```

**泰文语义 100% 丢失，向量完全由残存的数字和标点决定。**
它们之所以还"能区分"，是因为不同段落的数字不同 —— 这是**伪信号**。

后果有两层：
1. 这 1287 个 node（占索引 17%）在语义检索上是死的
2. 更糟的是，它们会在**数值类问题**上被数字巧合命中 —— 而数值类恰好是本项目已知的
   幻觉高风险区（详见 `docs/RAG_评估体系.md` 基线：numeric 类垃圾率 10.4%）。
   这与"表格 HTML 碎片在数值问题上顶到 top-1"是同一类故障的叠加。

## 三、多语言 embedding 是怎么统一语言的

三个层次，缺一不可：

### 第一层：共享子词词表

SentencePiece 在 100+ 语言混合语料上训练单一词表（XLM-R 是 250k）。这让各语言都能被切成
有意义的子词，而不是 `[UNK]`。

**但这只是必要条件。** 光有词表，`ทุเรียน` 和 `榴莲` 仍然是毫不相干的两个 token ID。

### 第二层：共享编码器与单一向量空间

所有语言过同一套 Transformer 权重，输出到同一个空间。这让"对齐"在物理上成为可能，
但还没有发生。

### 第三层（真正起作用的）：平行语料上的对比学习

训练时喂入大量翻译对，用 InfoNCE 之类的对比损失：

```
("榴莲叶片病斑", "Durian leaf spots")        → 拉近（正样本）
("榴莲叶片病斑", "曼谷榴莲价格上涨")           → 推远（负样本）
("榴莲叶片病斑", "Bangkok durian prices")     → 推远（负样本）
```

损失函数只关心"互为翻译的要比不相关的更近"。反复优化后，模型被迫学到一种
**编码语义、抑制语言身份**的表示。

## 四、实测二：跨语言对齐确实有效，但严重不均衡

用本地已有的 `bge-reranker-v2-m3`（基于 XLM-R，多语言）做 cross-encoder 打分。
查询固定为中文，文档分别是各语言的同义句与无关句：

```
中文查询: 榴莲叶片出现病斑，从叶尖开始扩展

文档            相关性分数
──────────────────────────
英文-同义          5.640   ← 与中文几乎并列第一
中文-同义          5.621
马来文-同义        2.038
泰文-同义         -1.961   ← 排序正确但明显偏弱
中文-无关         -8.801
英文-无关        -11.005
泰文-无关        -11.020
```

**两个读数：**

1. **跨语言对齐是真实有效的。** 英文同义句 5.640 与中文同义句 5.621 几乎并列，
   而三条无关内容全部掉到 -8 以下。语言差异没有构成障碍，语义相关性主导了排序。

2. **但对齐质量在语言之间存在数量级差距。** 泰文同义句 -1.961，虽然仍压过所有无关内容
   （排序正确），却明显落后于英文的 5.640。马来文 2.038 印证了同一梯度：

   ```
   高资源语言对（英-中）  ≈ 5.6   平行语料极多
   中资源（马来-中）      ≈ 2.0
   低资源（泰-中）        ≈ -2.0   平行语料稀少
   ```

   根因是训练语料规模，不是模型缺陷。这是所有多语言模型的共性。

## 五、相同含义的不同语言，向量不会相同

余弦相似度典型落在 0.8–0.95，**永远不是 1.0**。三个结构性原因：

1. **训练目标是"拉近"而非"重合"。** 只要翻译对比无关对更近，损失就下降了，模型没有
   动力把它们压成同一个点。
2. **语言身份信息不会被完全消除。** 多语言向量空间里语种仍是一个可分离维度 ——
   有做法会显式减去"语言中心向量"来缓解，这本身就证明问题存在。
3. **语义本身不完全等价 + 分词粒度不同。** `榴莲` 与 `durian` 所指相同，但在各语言语料中
   的搭配分布、文化联想不同；同一句话中文 11 token、英文 10、泰文 6，池化后的向量不可能一致。

## 六、结论：为什么离线翻译更好

| 方案 | 泰文内容效果 | 英文内容效果 | 代价 |
|---|---|---|---|
| **换 `bge-m3`** | 从"语义全丢"提升到**可用但偏弱**（对齐分数 ≈ -2） | 提升到接近中文水平 | 重建索引、模型 ~2GB、显存与延迟上升 |
| **离线翻译入库** ✅ | 提升到与中文内容**完全同等** | 同等 | 一次性翻译成本；失去原文精确引用 |

核心论证：

**换多语言模型，是把跨语言对齐的负担交给模型在检索时实时承担** —— 而实测显示模型在
泰语这类低资源语言上的对齐能力只有英语的零头（-1.961 vs 5.640）。

**离线翻译，是在入库阶段就把跨语言问题消灭掉** —— 检索时是纯中文对纯中文，
完全不依赖模型的跨语言对齐能力，因此不受语言资源不均衡的影响。

对英文文献，两个方案差距不大（英-中对齐本来就好）。
**但对占索引 17% 的泰文内容，离线翻译的效果明显优于换模型。**

### 附带收益

- 保持现有 `bge-small-zh-v1.5` 轻量模型，不动显存预算（远端 5090 已被 vLLM 占满）
- 与"重新分片"顺路完成，不增加独立工期
- 翻译产物是可审阅的中文文本，出问题能人工核对；模型内部的对齐质量无法审阅
- 检索侧代码零改动

### 代价与为什么可以接受

**失去泰文/英文的原文精确引用能力。**

本项目有"精确原文填空"需求（`rag_llamaindex.py:178` `is_exact_answer_query`），
依赖字面文本匹配。但该需求针对的是**中文内容**，泰文手册与英文文献本来也不用于填空。
因此这个代价可以接受。

**缓解措施：** 翻译后的 chunk 在 metadata 里保留原文（`original_text`）与语种标记
（`src_lang`），`index_text` 用中文译文供检索，需要引用原文时从 metadata 取。
这正好契合已经确立的 **`index_text` / `display_text` 分离**原则
（见 `docs/RAG_表格图片向量化_实施流程.md` 第二节）。

## 七、落地要点

1. **翻译对象**：泰文 3 份手册（651 chunk → 1287 node）+ 英文文献中的正文部分。
   FAQ（2476 node，中文）和 SOP/LKE（643 node，中文）不需要处理。

2. **翻译器**：优先用远端已有的 vLLM `durian-lora`（`127.0.0.1:8010`），零额外成本。
   泰文若质量不佳，改用 qwen-vl-max 所在的 API 通道（该 provider 支持纯文本模型）。

3. **必须做幂等缓存**：以 chunk 的 `text_sha1` 为 key 存 `rag_build/translations.jsonl`，
   重跑管道不重复付费。与图片 VLM 描述缓存同一套机制。

4. **保留原文**：`metadata.original_text` + `metadata.src_lang`，
   不要覆盖。这是唯一一次能拿到原文的机会 —— 泰文源 docx 已丢失，
   现存 chunk 是仅存副本。

5. **术语一致性**：翻译前先固化榴莲领域术语表（品种名、病害名、农事操作），
   作为 prompt 的一部分，避免同一术语在不同 chunk 里译法不一致而割裂检索。

6. **验收**：翻译完成后重跑 `rag_eval.py audit-gold` + `baseline`。
   预期 `zh→th`（21 条）与 `zh→en`（220 条）金标从"跨语言、排除在主指标外"
   转为可进入核心口径 —— **核心口径样本量从 13 条扩大到百条量级**，
   这会顺带解决评估体系当前最大的缺陷（见 `docs/RAG_评估体系.md` 第五节）。

> 第 6 点是个重要的额外收益：离线翻译不只改善检索，还让评估体系本身变得可信。

## 八、复现方式

本文档的实测数据可复现：

```bash
# 分词器对比（中文单语 vs 多语言）
.venv/bin/python - <<'EOF'
from transformers import AutoTokenizer
zh=AutoTokenizer.from_pretrained('models/bge-small-zh-v1.5')
ml=AutoTokenizer.from_pretrained('models/bge-reranker-v2-m3')
print(zh.vocab_size, ml.vocab_size)
for tok in (zh, ml):
    t=tok.convert_ids_to_tokens(tok.encode('จุดเด่นของทุเรียนชุมพร', add_special_tokens=False))
    print(t)
EOF

# 跨语言相关性打分（需要 torch）
```
