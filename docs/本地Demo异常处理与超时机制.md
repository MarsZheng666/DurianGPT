# 本地 Demo 异常处理与超时机制

**范围**：本文只覆盖三个本地 LangGraph demo 文件，梳理其中工具调用、LLM 调用、检索链路的异常处理、超时设置与恢复方式。生产链路（`durian__inference_api.py` 的 RAGFlow / vLLM 远程调用）不在本文范围内。

| 文件 | 定位 | 运行模式 |
|---|---|---|
| `langgraph_tool_demo.py` | 纯 agent⇄tools 循环最小 demo | 默认连 vLLM；`--fake` 离线 |
| `langgraph_agent_full_demo.py` | 全链路骨架（route→retrieve→compose→agent⇄tools→trim） | `FAKE_MODE=True` 默认离线 |
| `langgraph_dual_path_demo.py` | 双路径：强制 RAG 闭环 + ReAct Agent（15 步流程） | 纯 fake，`agent_node` 写死走替身 |

三个 demo 都能在不依赖任何外部服务的情况下离线跑通（fake 模式），异常处理的设计意图主要在"真模型"分支和图的循环控制上体现。

---

## 一、总体设计哲学

demo 层的异常处理遵循一条贯穿的原则：**错误不中断图，而是转成信息回填给模型，让模型自己消化**。

这与 LangGraph 的默认行为形成对照：节点函数抛出的异常默认会中断整个图的执行。demo 在关键位置（工具执行）主动用 try/except 把异常拦截下来，转换成 ToolMessage 继续循环；而在另一类位置（LLM 调用）则有意让异常直接抛出终止运行。即：

- **工具层：失败是预期内的**——工具报错、工具不存在，都回填字符串，循环继续；
- **模型层：失败是致命的**——vLLM 不可用意味着整条链路没有意义，直接 raise 终止。

这个分层本身是合理的设计意图，值得在接入生产时保留。

## 二、工具调用的异常处理

### 2.1 错误回填模式（tool_demo / agent_full_demo）

`tools_node` 对每一次工具调用做 try/except 包裹（`langgraph_tool_demo.py:184-189`、`langgraph_agent_full_demo.py:232-235`）。任何执行异常都被转成 `工具执行失败: {异常信息}` 字符串，包成 ToolMessage 回填，agent 循环继续，由模型在下一轮决定如何向用户解释。

这样做的价值：

1. **不打断图**。ReAct 循环中某个工具失败，其他工具的结果仍然可用，模型可以基于部分信息回答或坦诚说明哪个查询失败了。
2. **错误信息对模型可读**。异常以自然语言形式进入对话，模型有机会做二次决策（换个参数重试、换别的工具、或直接告诉用户）。

与之配套的还有**未知工具的优雅处理**：模型点了一个 `TOOL_IMPLS` 里不存在的工具名时，不抛异常，而是回填 `未知工具: {名称}`（`langgraph_tool_demo.py:185`）。这防御的是模型幻觉出不存在的工具名这一常见故障。

### 2.2 dual_path_demo 的差异：没有 try/except

`langgraph_dual_path_demo.py` 的 `tools_node`（255-270 行）用的是 if/elif 分发，**整体没有 try/except**。它不炸的原因是纯运气式的：三个工具（天气/土壤/知识库）全是字典查找和本地函数，参数也用 `.get()` 带默认值取，结构上不存在能抛异常的路径。

但这是三个 demo 之间的**模式不一致**：同样是工具执行节点，两个有异常回填、一个没有。如果以 dual_path_demo 为模板往生产搬（它的 15 步流程是最完整的），这个缺口会被一起带走——接上真实工具（HTTP 调用、数据库查询）后，任何一次工具异常都会直接中断整张图。

### 2.3 工具执行没有超时

三个 demo 的工具执行都没有任何超时机制（无 `asyncio.wait_for`、无线程池 timeout）。demo 工具都是瞬时完成的本地操作，这不构成问题；但"工具执行必须有上界"这件事在 demo 里完全没有体现，一旦换成真实的网络型工具（如 `search_kb` 对应生产中的 RAGFlow 检索），一个 hang 住的工具会拖死整个 agent 循环。

### 2.4 工具错误没有重试

工具失败回填后，**是否重试完全交给模型决策**——编排层没有"同一个工具失败后自动再试一次"的逻辑。这是刻意的 ReAct 设计（重试决策交给模型），但意味着没有兜底：模型如果不主动重试，失败就定格了。

## 三、LLM 调用的异常处理（真模型分支）

`langgraph_tool_demo.py` 的 `agent_node` 和 `langgraph_agent_full_demo.py` 的 `agent_node`（非 fake 分支）用 requests 直连 OpenAI 兼容接口，模式一致：

### 3.1 超时：有，60 秒

`requests.post(..., timeout=60)`（`langgraph_tool_demo.py:147`、`langgraph_agent_full_demo.py:207`）。对 demo 场景（单轮、非流式、短上下文）是够用的量级。没有重试：超时或网络错误直接抛 `requests.exceptions`，demo 层无 catch，图中断，进程以 traceback 退出——对学习 demo 而言是合理的"快失败"。

### 3.2 定向错误 + 可操作修复指引

`langgraph_tool_demo.py:149-156` 有一处值得单独记下的设计：对 **400 且响应文本含 `enable-auto-tool-choice`** 的错误，不做通用报错，而是抛出一个带完整修复步骤的 RuntimeError——明确指出是服务端 vLLM 缺启动参数、需要补哪两行、改完重跑即可。

这是"**已知错误模式 → 定向诊断信息**"的模式：识别出错误的具体成因，把 remediation 直接写进错误消息。比裸抛 `400: Bad Request` 的排查成本低一个量级。（`langgraph_agent_full_demo.py` 没有这段，非 200 一律通用报错，属两文件间的实现差异。）

### 3.3 其余非 200：直接 raise

其它状态码统一抛 `RuntimeError(f"vLLM 返回 {status}: {文本前300字符}")`，截断响应文本避免日志爆炸。无重试、无降级。

### 3.4 离线替身（fake 模式）本身没有异常路径

三个 fake 模型替身都是确定性逻辑，不涉及异常处理；它们的作用是把"图的循环机制"和"模型行为"解耦，让循环控制可以在无 LLM 环境下单独验证。这个解耦本身是异常处理调试的前提——出问题时能先排除模型变量。

## 四、检索链路的异常处理（dual_path_demo 路径 A）

dual_path_demo 的路径 A 是"检索 → 重排 → 证据判断 → 生成/改写重查/拒答"的闭环，它演示的不是"网络故障怎么办"（检索是本地函数，无网络），而是**业务层面的失败处理**：

### 4.1 MAX_RETRIES=2：改写重查是业务重试，不是错误重试

`MAX_RETRIES = 2`（`langgraph_dual_path_demo.py:27`）限制的是"证据不充分 → 改写查询 → 重新检索"的循环次数。它处理的是"**检索成功了但结果不够好**"这类质量型失败，而不是"检索本身抛异常"这类错误型失败——后者在 demo 里根本不存在处理路径。

这个区分很重要：生产中的检索异常（超时、隧道断、HTTP 5xx）在 demo 的图结构里没有对应节点行为，`retrieve_node` 如果抛异常会直接中断图。

### 4.2 refuse 节点：优雅终止替代硬答

重试耗尽后走 `refuse_node`（214-221 行）：输出"知识库中暂无足够可靠的资料……请补充具体品种、环境、症状细节"的诚实拒答。这是整条异常处理链路里最完整的一个"恢复"设计——**失败被转换为对用户有明确引导价值的输出**（告诉用户缺什么信息、补充后可重新检索），而不是报错或静默。

### 4.3 grade 的充分性判据设计

`grade_node`（173-184 行）除了分数阈值外，还要求问题里的**核心症状词被证据覆盖**才算充分——"搜到了东西"不等于"能支撑回答"。这与异常处理的关系在于：它防的是检索侧"返回了看似相关的噪声"这种最难察觉的静默失败。

## 五、循环控制与终止保障

demo 中存在两个循环，控制方式不同：

| 循环 | 控制机制 | 兜底 |
|---|---|---|
| grade → rewrite → retrieve（dual_path 路径 A） | `retry_count < MAX_RETRIES` 显式计数（310-311 行） | 超限走 refuse，**有界** |
| agent ⇄ tools（三个 demo） | 条件边：无 tool_calls 即终止 | **无显式步数上限** |

agent⇄tools 循环没有自己的最大轮数限制。如果模型陷入"永远发起工具调用"的病态（工具一直失败、模型一直换姿势重试），demo 层没有拦截。实际兜底来自 **LangGraph 框架默认的 `recursion_limit=25`**：超过会抛 `GraphRecursionError` 中断图。这是隐式保障——能防死循环，但报错形式是框架异常而非可控出口，且 25 这个默认值不是显式声明的意图。

## 六、恢复机制总表

| 故障场景 | demo 现状 | 恢复方式 |
|---|---|---|
| 工具执行抛异常 | 回填错误字符串给模型 | 模型自行决策（可能换工具/换参数/告知用户） |
| 模型点名不存在的工具 | 回填"未知工具"字符串 | 模型自行修正 |
| 工具 hang 住 | 无超时，永久等待 | 无 |
| LLM 请求超时/网络错误 | 60s 超时后 raise | 无自动恢复，人工重跑 |
| vLLM 未开 tool-choice（400） | 定向错误消息 + 修复指引 | 人工按指引改服务端后重跑 |
| 证据不充分（质量型失败） | 改写重查，上限 2 次 | 耗尽后诚实拒答 + 引导补充信息 |
| agent 无限循环调用工具 | 无显式上限 | LangGraph 默认 recursion_limit=25 框架级中断 |

## 七、缺口与建议（若 demo 接入生产）

按优先级：

1. **补齐 dual_path_demo 的 tools_node 异常回填**。它是最可能被当作生产模板的文件，却缺了另外两个 demo 都有的 try/except 模式。统一成"错误转 ToolMessage 回填"，迁移时才不会把裸奔的工具执行带走。

2. **给工具执行加超时上界**。工具函数应当包一层 `asyncio.wait_for`（或线程池 + timeout），单工具 10-30 秒视工具性质而定。超时和报错同样转字符串回填给模型——模型看到"工具超时"后可以放弃该信息源继续回答，这比整个请求 hang 死好得多。

3. **给 agent⇄tools 循环加显式步数上限**。不要依赖框架默认的 recursion_limit=25。在 state 里加一个循环计数器，超限时走一个"信息不足，已尝试 N 次工具调用"的收尾节点（类似 dual_path 的 refuse 模式），把无界风险变成有界且对用户友好的出口。

4. **区分"检索异常"与"检索为空"**。demo 的图结构只处理了后者。接入真实检索后，retrieve 节点应 catch 检索异常并显式标记（如 `evidence_error: true`），异常时可以直接降级走拒答路径，而不是让"服务挂了"伪装成"没搜到"。

5. **LLM 调用的有限重试（可选）**。对连接类错误重试 1 次、短退避，对超时和 4xx 不重试。demo 里可以不做，但接入生产前值得补上——单次网络抖动不应该让整轮对话失败。

6. **保留的既有优点**：错误回填模式、未知工具防御、定向错误+修复指引、refuse 的诚实拒答设计，这四个模式在生产中都值得原样保留。
