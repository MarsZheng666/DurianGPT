# RAG 效果评估体系

> 用于重新分片前后的效果对比。工具：`rag_eval.py`，产物在 `rag_eval/`
> 建立日期：2026-09-02

---

## 一、为什么需要三个口径而不是一个数字

建这套体系过程中踩到一个关键陷阱，值得先讲：**第一版评估跑出 Hit@5 = 3.2%**，但人工抽测 8 个真实问题时 8/8 都返回了对题的内容。这个矛盾说明数字是错的，不是检索是错的。

逐层排查后发现三个独立的失真源：

| 失真源 | 表现 | 修法 |
|---|---|---|
| **长锚点跨 chunk** | 金标 `source_text` 的自然语言片段常达 100-180 字符，而索引 chunk 中位仅 322 字符，长锚点做包含匹配必然假阴性 | 锚点改为归一化后的 **24 字符定长短窗口**，一条金标取多个窗口，命中任一即算召回 |
| **锚点本身是垃圾** | 部分锚点从 MinerU 残渣派生，形如 `blocks00blockshtml1seedlingdieback`、`40502403673593`（bbox 坐标） | `anchor_is_junk()` 过滤：残渣词根、数字占比 >45%、字母占比 <60% |
| **语料根本不含该内容** | 金标由 `clean_chunks.jsonl`(9402) 生成，但索引只有 7668 node，文献部分从 7751 掉到 3262。**45.5% 的金标内容压根不在索引里** | 引入可达性预检 `audit-gold`，把"内容缺失"与"排序不佳"分开 |

修完后核心口径 Hit@5 从 3.2% 升到 **69.2%**，与人工观感一致。

**教训：任何低到反常的指标，先证明指标本身可信，再下结论。** 否则会把精力浪费在优化一个不存在的问题上。

## 二、三个口径的定义与用途

```
全量金标 255 条
  └─ 可达 139 条 (54.5%)          ← 内容确实在索引里
       └─ 核心 13 条              ← 可达 ∩ 同语种，唯一可干净归因
```

| 口径 | n | 含义 | 什么时候看 |
|---|---|---|---|
| **全量** | 255 | 端到端体验，含语料缺失与跨语言干扰 | 对外汇报整体水位 |
| **可达** | 139 | 排除了内容缺失，但含跨语言干扰 | 判断检索召回能力 |
| **核心 ★** | 13 | 可达 ∩ 同语种 | 判断纯排序质量。**样本过小，见第五节** |

分开的理由：重新分片后如果 Hit@5 上升，必须能回答"是因为内容被挽回，还是因为排序变好"。混在一个数字里就无法归因，也就无法判断下一步该优化什么。

## 三、指标清单

### 正向 —— 该找到的有没有找到

| 指标 | 定义 |
|---|---|
| Hit@k | 前 k 条证据中有任一命中金标锚点 |
| MRR | 首个命中位置的倒数均值，惩罚排名靠后 |
| nDCG@5 | 位置折损累积增益 |

### 答案支撑度 —— 跨语言可用（本项目主力）

金标 94% 是"中文提问 + 英文/泰文原文"，原文锚点匹配在这种情况下会把"召回了语义正确的中文证据"误判为失败。但金标 `answer` 是中文，召回证据也主要是中文，所以改为度量答案要点的支撑情况：

| 指标 | 定义 |
|---|---|
| **要点覆盖率** | 金标答案的实义要点（数值+单位、品种代号、2-4 字中文词，去停用词）在召回证据中的命中比例 |
| **支撑率** | 覆盖率 ≥ 0.35 的问题占比 |

这是弱于锚点法的判据（不能证明来源同一），但跨语言稳定，且**同一套判据下的相对变化仍然可信** —— 这对 before/after 对比足够。

### 三类"假阳性"必须扣除（2026-09-02 补）

金标以 FAQ 为主源后，出现三种会让指标虚高的情况，报告中分别处理：

| 情况 | 表现 | 处理 |
|---|---|---|
| **自命中** | FAQ 问答对本身在索引里，用其问题检索必然命中自己。实测英文 FAQ 的 top1 **100%** 是自命中，Hit@3 因此虚高到 100% | `_is_self_hit()` 标记，给出 `*` 口径 |
| **跨语言金标污染** | legacy 的 243 条"中文提问+英文原文"混进 `by_lang`，把中文那一行从 **53.4% 拉低到 36.5%** | `by_lang` 只统计同语种金标，全量另存 `by_lang_all` |
| **FAQ 平行命中** | FAQ 有 en/zh/th/ms 四个平行版本，英文问题会命中中文版同一条问答。实测占召回 **88%** | `_is_qa_chunk()` 标记，给出 `†` 知识库口径 |

⚠️ **`†` 口径对 FAQ 金标不适用。** 扣掉 91% 的 FAQ 证据后平均只剩 0.4 条，
此时度量的是"残渣里有没有答案"。已加 `kb_valid`（剩余非 FAQ 证据 ≥2 条）门槛，
样本不足时直接标「样本不足」而非报 0。

**关键交叉验证**：legacy 金标（问题由文献生成）的 FAQ 证据占比只有 **8-11%**，
与 FAQ 金标的 91% 差一个数量级。这证明**不存在"FAQ 挤占知识语料"的系统性问题**，
是 FAQ 问题匹配 FAQ 内容的合理行为。若只看 FAQ 金标的 91% 就下结论，会误判为架构缺陷。

### 负向 —— 找回来的是不是垃圾（含独立判据交叉验证）

⚠️ **必看 `independent_defect()` 而非只看 `evidence_defect()`。**
后者的正则与 `rag_rechunk.py` 的清洗正则同源，用清洗规则检验清洗结果必然满分 ——
2026-09-02 重新分片后实测：管道判据报 0.0%，独立判据报 **27%**（残留孤立引号
`'3 kg'` 与裸 bbox 坐标 `13, 488, 409, 547`）。修完后独立判据降到 0.8%。

独立判据换一个维度：不问"有没有 MinerU 残渣特征"，而问"**像不像人写的句子**"，
四条规则与清洗管道零共享：

| 规则 | 判据 |
|---|---|
| `struct_symbol` | 含 `{}` 或 `[48, 136` 这类坐标数组开头 |
| `stray_quotes` | 引号计数 ≥4 |
| `number_run` | 连续 4 个以上纯数字 token |
| `low_text_ratio` | 文字字符占比 <0.5 |

**方法论**：评估判据与被评估对象共享实现时，指标必然虚高。任何"完美"的指标
都要用独立实现的判据交叉验证。这与"低到反常的指标先怀疑指标"是同一条原则的两面。

### 负向指标清单

这组指标是本项目的关键。只看召回率会完全掩盖"召回了但是垃圾"，而这恰是当前语料的主要问题。

| 指标 | 定义 |
|---|---|
| 证据垃圾率 | 召回证据中不可用的占比 |
| **Top1 垃圾率 ★** | 排第一的就是垃圾。危害最大 —— LLM 最信任首条证据 |
| 空结果率 | 完全没召回的问题占比 |

垃圾判据 `evidence_defect()`：裸表格 HTML（`<td>` 无表头，数值幻觉高风险）、MinerU 残渣、字母占比 <55% 的噪声、长度 <30 的碎片。

### 性能

P50 / P95 检索延迟。

## 五、这套体系目前的缺陷（必须知道）

**核心口径只有 13 条，统计上不足以做验收依据。** 根因是现有 QA 数据集不适合当检索金标：

- `qa_dataset.jsonl` / `qa_dataset_v2.cleaned.jsonl` 共 255 条可用，其中 **241 条是"中文提问 + 英文/泰文原文"**（`zh→en` 220、`zh→th` 21），同语种仅 14 条
- 金标 `doc_id`（如 `doc_409`）是 `clean_chunks.jsonl` 的行号指针，**重新分片后必然失效**，无法用 ID 匹配
- 133 条因无法提取有效锚点被弃用

**补救建议（按性价比）**：

1. **离线把泰文/英文语料翻译成中文入库**（最高优先，且顺路解决检索问题）。
   这会让 `zh→th`(21) 与 `zh→en`(220) 共 241 条金标从"跨语言、排除在主指标外"
   转为可进入核心口径，**样本量从 13 条扩大到百条量级**。
   详见 `docs/RAG_跨语言检索方案.md` —— 实测证明对泰文这类低资源语言，
   离线翻译效果优于换多语言 embedding。
2. **人工标注 50-80 条中文金标**。覆盖六类问题，每条标注问题、正确答案、
   支撑该答案的中文原文片段。可从 FAQ 的 2476 个干净中文 node 里挑内容出题。
3. **用答案支撑度作为过渡主指标**。它跨语言稳定，绝对值不能解读为"准确率"，
   但相对变化可信。
4. 保留跨语言金标作参考口径，不进主指标。

## 六、使用方式

```bash
# 1. 构建金标集（含语种标注、答案要点抽取）
python rag_eval.py build-gold

# 2. 可达性预检 —— 每次重建索引后都要重跑
python rag_eval.py audit-gold

# 3. 跑评估存报告
python rag_eval.py baseline --tag before_rechunk

# 4. 重新分片、重建索引后再跑一次
python rag_eval.py audit-gold
python rag_eval.py baseline --tag after_rechunk

# 5. 对比
python rag_eval.py compare --before before_rechunk --after after_rechunk

# 查看已有报告
python rag_eval.py show --tag before_rechunk
```

产物：

| 文件 | 内容 |
|---|---|
| `rag_eval/gold.jsonl` | 金标集，含 anchors / answer_terms / 语种标注 |
| `rag_eval/gold_audit.json` | 可达性预检结果，含可达/不可达 qid 清单 |
| `rag_eval/report_<tag>.json` | 完整报告，含逐题明细 `rows` |

`compare` 会输出逐题变化清单：**新召回成功**和**召回退化**的题目数与 qid。退化题目必须人工复核 —— 平均值改善但个别退化，往往意味着引入了新的失效模式。

## 七、重新分片的验收标准

| 指标 | 基线 | 目标 | 理由 |
|---|---|---|---|
| **语料可达率** | 54.5% | **≥ 85%** | 主要收益来源。按 block type 正确分流后，不该再有 45% 内容被噪声过滤器丢掉 |
| **Top1 垃圾率** | 9.0% | **≤ 2%** | 表格转 Markdown、图片转描述后，裸 HTML 碎片应基本消失 |
| 证据垃圾率 | 8.5% | ≤ 3% | 同上 |
| 答案要点覆盖率（全量） | 9.6% | ≥ 25% | 内容挽回 + 表格可读的综合体现 |
| variety 类 Top1 垃圾率 | 17.4% | ≤ 3% | 品种对照表恢复表头后应显著改善 |
| numeric 类垃圾率 | 10.4% | ≤ 3% | 数值类是幻觉高风险区，必须重点验收 |
| P95 延迟 | 252ms | ≤ 400ms | 表格整块 node 会变长，允许小幅上升 |
| 空结果率 | 0.0% | ≤ 5% | 加了质量过滤后允许上升 —— **返回"证据不足"优于返回错答案** |
| **核心口径样本量** | 13 条 | **≥ 100 条** | 离线翻译后跨语言金标转为同语种，主指标才统计上可信（见 `docs/RAG_跨语言检索方案.md`） |
| 同语种金标占比 | 5.5%(14/255) | ≥ 80% | 同上 |

最后一条是有意的取舍：宁可不召回，不可召回残表。

## 八、后续可扩展的评估维度

当前体系只覆盖**检索**层。完整的 RAG 评估还应包括：

1. **生成质量**：忠实度（答案是否只依据证据）、答案相关性。需要 LLM-as-judge 或人工。
2. **幻觉专项**：针对数值类问题，检查答案数值是否与证据中数值一致。这是本项目最该补的一项。
3. **拒答能力**：构造知识库中确实没有的问题，检验是否正确拒答而非编造。
4. **图片/表格召回专项**：重新分片引入图片描述和 Markdown 表格后，需要专门的金标验证这两类内容能否被检索到。
