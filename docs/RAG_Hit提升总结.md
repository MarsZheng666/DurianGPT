## 二、泰文：0.6% → 98.8% 的五步

### 步骤 1｜BM25 泰文 n-gram 分词（ Hit@3 2.2% → 94.2%）

**根因**：泰文书写不用空格，`_lexical_terms()` 对泰文输出 **0 个词条**——词法通路完全空转，泰文查询只靠已塌缩的 dense（所有泰文短查询映射到常量向量）。

**改动**：`rag_llamaindex._lexical_terms()` 补泰文 3-4 字符 gram（一个音节常占 3-4 字符，中文用 2-3）。

### 步骤 2｜术语表别名双向扩展 + 泰文条目 5 → 101 条

**根因**：泰文查询的品种名/病害名（语料 476/594 次）无法跨语种命中；初测"92.8% 查询有扩展"是假的——剔除零区分度的「榴莲」组后真实基线只有 **1.4%**。

**改动**：`glossary.json` 拉平为双向别名索引（同一标准名下所有写法互为别名）；泰文条目用 651 条平行句对做统计对齐扩充（译名以项目中文语料既有用法为准，不自创）。有区分度的扩展覆盖 **1.4% → 94.2%**。

### 步骤 3｜泰文声调符号规范化（卫生工程 + 短查询 +10pp）

**根因**：legacy 泰文 .docx 有**两套互不相容的字符损坏方案**（一份是预组合 `ำ` 被分解，一份是 `ํ`=`่`/`๎`=`้` 字形错映射），加一整类藏在**非泰文码位**的坏字符（U+02DA RING ABOVE 1250 处，此前所有统计都漏了）。共 6 类损坏、6867 处。

**改动**：`normalize_thai()` 按文档判损坏方案（判据一个正则、651 chunk 上 0 误判），建索引/查询/dense 三侧同步应用（**必须三侧同步**——RRF 按文本去重键合并，单侧改文本会把同一 node 劈成两条、分数掉 50 倍）。

**价值画像（三场景实测）**：聚合指标 0.0pp（BM25 的 gram 冗余天然容忍稀疏损坏）、短查询 +10~13pp（查询几乎全部 gram 落在损坏位时规则是唯一通路）、展示层正确泰文。**卫生基础设施 + 短查询场景的真实检索价值。**

### 步骤 4｜651 条 index_text 双语拼接（ known-item 0.6% → 94.5%）

**根因（本次最大的一个发现）**：`load_rechunk_nodes()` 只对表格/图片/QA 转存 `original_text`，`block_type=="text"` 走另一支——**651 条泰文正文的原文在建索引时就被丢弃了，索引里只剩中文译文**。泰文查询在词法上对这批知识库正文完全不可见（docstore 里 `original_text` 出现 0 次）。这就是"Hit@3 94.2% 但覆盖率卡 51.2%"的真解：命中的全是 FAQ。

**改动**：`index_text = 中文译文 + "\n" + 泰文原文`，并**绕过 SentenceSplitter**（实测 splitter 会把拼接文本按语言干净地切成两块，等于白拼）。三个前置验证：拼接后 bge token median 207/max 343（0/651 超 512，泰文 500 字符只压成 60 token）；中文在前让 embedding 由中文主导；中文侧 known-item 零退化（98.2%→98.2%）。

### 步骤 5｜泰文查询跳过 dense（ known-item 94.5% → 98.8%）

**根因**：bge-small-zh（中文单语，vocab 21128）对泰文查询的编码是纯噪声——UNK 占比中位 66.7%，**139 条查询只剩 13 个不同 token 序列**——却在 RRF 里占 1.0 权重，把 BM25 的正确结果挤出 top-k。

**改动**：`_is_thai_query()`（判据 `泰文字符 ≥ 中文字符 × 3`，×3 修正泰文字符膨胀，泰文 139/139 全中、非泰文 1108 条假阳性 0）→ dense 不参与融合。

**归因严格性**：+4.3pp 经 **2×2 完整分解**定死（跳过 dense = 全部收益，规范化规则边际 0.0pp），McNemar p<0.0001，中文/英文/马来文 `hit@3_ns` 变化 +0.0000（零溢出）。曾一次被误撤回到"+0.0pp"——那是测量者拿已含改动的现状冒充基线臂所致。**「现状」≠「基线」。**

## 三、马来文：58.9% → 85.4% 的两步

### 前提｜先修量具，再动语料

- **Hit@1 66.5% 是假象**：马来文 FAQ 金标近重复饱和（最近邻 Jaccard 中位 0.632 vs 英文 0.421；"近乎同题"占 28.9%），Hit@1 测的是"从 5 个改写版里挑中指定那一条"。放宽口径后 66.4→80.3%。
- **文档检索从未被测过**：152 条金标全是 FAQ 自检索。补建 known-item 集后才测出真实数字 **58.9%**，并抓到**单调剂量曲线**：源 chunk 0-400 字符 Hit@5 96.1%，700-900 字符只有 65.5%。

### 第 1 步｜换 2024 官方新版（一步解决四个问题）

**根因**：同一本 62 页的书在库里**被索引了两次**——`MY_DOA_2012`（145 chunk，文本干净但中位 825 字符、超过全库 p90）+ `pt_durian`（420 chunk，粒度好但注入 26 处中文幻觉、`tanah`(土)被 OCR 成 `tidak`(不)——**"用土填坑压实"变"不用填坑压实年份"，反义改词是合法马来语、扫不出、不可枚举**）。合计 565 chunk 占全库 6.7%。

**改动**（三方共识方案 (c)）：下载官方 2024 新版（111 页，内容大幅扩充）→ 按文档粒度细切（`DOC_CHUNK_SIZE=300`，median 256）→ 两份旧解析出库 → 重建索引。

**关键实现决策**：
- overlap 必须与 size 等比：第一版 849 chunk 是 `CHUNK_OVERLAP=150` 绝对值在 size=300 下 = **50% 重叠**（会把"近重复挤占 top-5"烤进索引），改 `DOC_CHUNK_OVERLAP=50` 后 560 chunk、相邻衔接 median 0
- **粒度与清洁度首次兼得**：比旧干净血统 +47.8pp，比旧细切血统 +11.2pp 且文本干净

### 第 2 步（顺带）｜4 个受损 chunk 修复

`น้ำ`（水，灌溉语境高价值词）曾被旧规范化规则在建索引时烤成废词（不可逆，运行时无法追溯）——全量重建自动治愈。

## 四、评估体系修复（让所有数字可信）

1. **`q_lang` 根因修复**：346 条"英文"金标里 **237 条（68.5%）问题正文是纯中文**（按 FAQ 源文档语种标注所致）。改为按问题文本 `detect_lang()` 推导、`cross_lingual` 按"问题 vs 答案语言"判定。修正后真实英文（你的主要语种）**首次被单独测量：Hit@1 89.8% / Hit@3 100%**——好消息，此前的 100% 不是假象。
2. **known-item search 方法论**：查询取 chunk 前半片段、锚点取后半 24 字符窗口、两道自检（可达性审计 + 锚点垃圾过滤 + 词边界约束）。这是唯一能量化"知识库侧改动"的评测形态——FAQ 金标对泰文知识库口径**结构性恒为 0**（证据 100% 是 FAQ）。
3. **口径打架的取舍规则**：raw 被自命中虚高（泰文 94.2% vs 诚实口径 25.2%）；`_ns` 在近重复语料上被污染（曾据此得出一个错误结论后被反号推翻）；**两口径方向相反时以无污染口径为准**。

## 五、被实测否决的方案（勿重走）

| 方案 | 否决证据 |
|---|---|
| 查询侧翻译（泰→中/英再检索，含术语占位符全部 4 个变体） | dense-only 全部低于基线（纯术语映射 0.0%）。根因是跨语言向量鸿沟：**译文越像中文，越远离证据所在的泰文簇**。术语表 5→95 条后 Hit 一动不动证明与翻译质量无关 |
| 本地小翻译模型（m2m100/nllb/mesolitica） | 「榴莲」主体词 15/15 全丢；`opus-mt-th-zh` 不存在 |
| 马来文 dense 降权 w=0.4 | McNemar p=0.0654 不显著；无污染口径下最优权重定不出来。等金标扩容后重测 |
| 换多语言 embedding（bge-m3） | 2GB + 全量重建 + 中文单语质量风险；跨语言对齐分数显示泰文即使多语言模型也偏弱 |

## 六、五条可复用的方法论

1. **指标反常时先证明指标可信**（本项目七次应验）：低到反常 → 查量具；高到反常也查（英文 100%、泰文 94.2% 都是虚高）。
2. **统计语料缺陷前，先确认那些文本真的会被检索**：`metadata.original_text` 的坏符号 5598 个，进索引的只有 19 个——「源文本频次」≠「索引文本频次」，本例差 300 倍。
3. **「现状」≠「基线」**：在已含改动的代码上做 A/B，基线臂必须显式还原改动。
4. **聚合指标会系统性掩盖子集收益**：规范化规则在长查询 0pp、短查询 +10pp——按查询长度分层评估。
5. **两侧同源的评测集测不出双侧规范化类规则的价值**：查询与语料同损坏时，双侧修复不改变匹配关系。
